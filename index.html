Algorithm patterns — 14 that cover almost everything

1. Two Pointers

Use when: sorted array, need pairs/triplets, or in-place partitioning.

Template: left=0, right=n-1; move based on comparison. Or both start at 0 with different speeds.

Classic problems: Two Sum II (sorted), 3Sum, container with most water, remove duplicates in place, Dutch national flag (partition).

Complexity: O(n) time, O(1) space — the win over hash-map approaches.

2. Sliding Window

Use when: contiguous subarray/substring with a constraint (max sum, longest without repeats, at most K distinct).

Template:

int l = 0;
for (int r = 0; r < n; r++) {
add(arr[r]);
while (!valid()) { remove(arr[l]); l++; }
best = Math.max(best, r - l + 1);
}

Key insight: the window only moves forward — that's why it's O(n) not O(n²).

Classic problems: longest substring without repeating characters, minimum window substring, max sum subarray of size K, longest subarray with at most K distinct.

3. Fast & Slow Pointers (Floyd's)

Use when: cycle detection, finding the middle, or detecting a repeating sequence in O(1) space.

Template: slow moves 1, fast moves 2. They meet inside a cycle. To find the cycle start: reset one to head, advance both by 1 until they meet.

Classic problems: linked-list cycle, find middle, happy number, find duplicate number.

Why it works: if a cycle exists, the fast pointer gains on the slow one by 1 each step and must eventually lap it. O(n) time, O(1) space.

4. Binary Search (and its variants)

Use when: sorted input, or a monotonic predicate ("find the first X such that condition is true").

The three variants you must distinguish:

  • Exact match: standard lo <= hi, return mid when equal.
  • Lower bound (first index where arr[i] >= target): lo < hi, hi = mid when arr[mid] >= target, else lo = mid+1.
  • Upper bound (first index where arr[i] > target): same but condition is arr[mid] > target.

Binary search on the answer: the most valuable variant at senior level. If the problem asks for a minimum/maximum value satisfying a monotonic condition, binary search the value, not the array. Examples: "minimum capacity to ship packages in D days", "Koko eating bananas", "split array largest sum".

Off-by-one is where people fail
Pick lo <= hi with hi = mid-1 / lo = mid+1 (exact match) or lo < hi with hi = mid (boundary). Mixing the two is the classic bug. Also: mid = lo + (hi-lo)/2 to avoid overflow.
5. BFS — level-by-level traversal

Use when: shortest path in an unweighted graph, level-order traversal, or minimum steps to a state.

Template: queue + visited set. Push start; while queue not empty, process all nodes at current level (record size before the inner loop).

Complexity: O(V + E) time, O(V) space.

Classic problems: word ladder, rotting oranges, shortest path in grid, level-order traversal, minimum depth of binary tree, connected components.

6. DFS — recursion and backtracking

Use when: explore all paths, detect cycles, topological sort, or any tree problem.

Template (recursive): visit node, mark visited, recurse into neighbours.

Template (iterative): explicit stack, push neighbours in reverse order for the same traversal order.

Complexity: O(V + E) time, O(V) space (recursion depth).

Classic problems: number of islands, clone graph, course schedule (cycle detection), path sum, validate BST, permutations/subsets (backtracking).

7. Backtracking

Use when: generate all combinations/permutations, or find a path satisfying constraints (N-Queens, sudoku).

Template:

void backtrack(State s, List<Result> out) {
if (isComplete(s)) { out.add(copy(s)); return; }
for (Choice c : choices(s)) {
if (!isValid(c)) continue;
apply(s, c);
backtrack(s, out);
undo(s, c); // <-- the essential line
}
}

Complexity: exponential — that's expected. Pruning is the optimisation.

The key discipline: always undo. If you forget the undo, you get a wrong answer, not a compile error. This is where people lose the round.

8. Dynamic Programming — the 4-step method

Use when: optimal substructure + overlapping subproblems. Signals: "minimum/maximum ways", "longest/shortest", "can you reach", "number of ways".

  1. Define the state. What does dp[i] or dp[i][j] mean? Write it in a sentence.
  2. Write the recurrence. dp[i] = f(dp[i-1], dp[i-2], ...).
  3. Base cases. The smallest inputs where the answer is obvious.
  4. Order of computation. Ensure dependencies are computed first. Then optimise space if possible.

9. Greedy

Use when: a locally optimal choice provably leads to the global optimum. The hard part is proving it — and interviewers will ask.

Classic problems: activity selection (interval scheduling), jump game, gas station, Huffman coding, minimum number of arrows to burst balloons.

How to tell greedy from DP: if you can prove an exchange argument (any optimal solution can be transformed to include the greedy choice without getting worse), it's greedy. Otherwise, DP.

10. Heap / Top-K

Use when: "K largest/smallest/most frequent", streaming median, merge K sorted lists.

Key trick: for K largest, use a min-heap of size K. Push each element; if size exceeds K, pop the smallest. The heap ends up holding the K largest. O(n log K) time, O(K) space.

Classic problems: Kth largest element, top K frequent words, merge K sorted lists, find median from data stream (two heaps), task scheduler.

QuickSelect is the O(n) average alternative for Kth largest — partition around a pivot like quicksort, recurse into one side only.

11. Merge Intervals

Use when: intervals, scheduling, overlap detection, meeting rooms.

Template: sort by start; iterate; if current start <= last end, merge (extend end); else push new interval.

Classic problems: merge intervals, insert interval, meeting rooms I/II, non-overlapping intervals, interval list intersections.

For "meeting rooms II" (max concurrent): use a min-heap of end times. For each meeting, pop all ended ones, push the end, track max heap size.

12. Trie (Prefix Tree)

Use when: prefix search, autocomplete, word dictionary, IP routing tables.

Node: Map<Character, Node> children; boolean isEnd;

Complexity: O(m) insert/search where m = word length. Space is the trade-off — can be large.

Optimisations to mention: compressed trie (radix tree) merges single-child chains; a ternary search tree trades some speed for memory.

Classic problems: implement trie, word search II, replace words, design search autocomplete.

13. Union-Find (Disjoint Set Union)

Use when: connectivity queries, cycle detection in undirected graphs, Kruskal's MST, grouping elements.

Two optimisations that make it near-O(1):

  • Path compression: during find, point every node directly at the root.
  • Union by rank/size: attach the smaller tree under the larger.

Together: O(α(n)) per operation, where α is the inverse Ackermann function — effectively constant.

int find(int x) {
if (parent[x] != x) parent[x] = find(parent[x]); // path compression
return parent[x];
}
void union(int a, int b) {
int ra = find(a), rb = find(b);
if (ra == rb) return;
if (rank[ra] < rank[rb]) { int t = ra; ra = rb; rb = t; }
parent[rb] = ra;
if (rank[ra] == rank[rb]) rank[ra]++;
}

Classic problems: number of connected components, redundant connection, accounts merge, graph valid tree, number of islands II.

14. Bit Manipulation

The tricks worth knowing:

  • n & (n-1) clears the lowest set bit — count set bits by looping until zero.
  • n & 1 tests odd/even; n >> 1 divides by 2.
  • n ^ n = 0, n ^ 0 = n — XOR finds the single non-duplicate element.
  • x & -x isolates the lowest set bit.
  • XOR swap: a ^= b; b ^= a; a ^= b; (interview curiosity, not production code).

Classic problems: single number, number of 1 bits, counting bits, reverse bits, missing number, power of two.

03Data Structures — Internals That Matter

At architect level, "I'd use a HashMap" is not an answer. "I'd use a HashMap because lookups are O(1) amortised, but I'd note the worst case is O(n) if the hash function is poor, and I'd size it to avoid resizing" is an answer. This section is the internals.

Hash Map — how it actually works

The structure

An array of buckets. Each bucket holds either a single node, a linked list, or a red-black tree (Java 8+). hash(key) → spread → index = (n-1) & hash.

Java's HashMap specifics

  • Initial capacity: 16. Load factor: 0.75. Resize doubles capacity when size > capacity × loadFactor.
  • Hash spreading: h = key.hashCode(); h ^= (h >>> 16) — XORs high bits into low bits so the index computation uses more entropy.
  • Treeification: when a bucket's chain exceeds 8 entries and capacity is ≥ 64, it converts to a red-black tree, changing worst-case lookup from O(n) to O(log n). It untreeifies below 6.
  • Resize cost: O(n) rehash. Pre-size with new HashMap<>(expected/0.75 + 1) if you know the size.
  • Not thread-safe. Concurrent modification throws ConcurrentModificationException on iteration. Pre-Java-8, concurrent puts could corrupt the map into an infinite loop.

What they ask

  • "Why is the load factor 0.75?" — Trade-off between time and space. Lower = fewer collisions, more memory. 0.75 is the empirically balanced default.
  • "Why treeify at 8?" — With a good hash, the probability of 8 collisions in one bucket is ~0.00000006 (Poisson). It's a safety net for pathological hash functions, not a common path.
  • "What happens if two keys have the same hashCode?" — They land in the same bucket; equals() distinguishes them. This is why the equals/hashCode contract matters.
The contract
If a.equals(b) then a.hashCode() == b.hashCode(). The reverse is not required. Breaking this — e.g. mutable fields in hashCode, or overriding equals without hashCode — silently breaks HashMap lookups. This is a favourite interview trap.

ConcurrentHashMap — how it achieves concurrency

  • Pre-Java-8: segment-level locking (16 segments by default). Different segments could be written concurrently.
  • Java 8+: lock-free reads (volatile reads of the bin head), and per-bin synchronized only for the first node when writing to a non-empty bin. Empty-bin insertion uses CAS. This gives much finer granularity than segments.
  • No null keys or values. Deliberate — nulls are ambiguous in a concurrent context (absent vs. present-but-null).
  • Size is an estimate. size() is not a snapshot; it's computed from counters and may be stale.
  • Iteration is weakly consistent. No ConcurrentModificationException; you may or may not see concurrent updates. This is why it's safe to iterate while others write.
  • Useful methods: computeIfAbsent, merge, compute — these are atomic, unlike a get-then-put sequence.
The architect answer
"I'd use ConcurrentHashMap for a shared cache, but I'd note that compound operations must use compute/merge to be atomic. A get-then-put is a race even on a concurrent map."

TreeMap & TreeSet — red-black trees

  • Ordered by natural ordering or a Comparator. Iteration is in sorted order.
  • O(log n) for get/put/remove — guaranteed, not average.
  • NavigableMap methods: firstKey, lastKey, floorKey, ceilingKey, higherKey, lowerKey, subMap, headMap, tailMap. These are why you'd pick it.
  • Use cases: range queries, ordered iteration, leaderboards, rate limiting with time buckets, LRU via LinkedHashMap (not TreeMap — see below).

LinkedHashMap — and the LRU trick

LinkedHashMap extends HashMap with a doubly-linked list threading through entries, preserving insertion order (or access order if constructed with accessOrder=true).

The interview trick: override removeEldestEntry to get a free LRU cache:

class LRUCache<K,V> extends LinkedHashMap<K,V> {
private final int capacity;
LRUCache(int capacity) {
super(capacity, 0.75f, true); // accessOrder = true
this.capacity = capacity;
}
@Override
protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
return size() > capacity;
}
}

In an interview, mention this and offer to implement the O(1) version with a HashMap + doubly-linked list from scratch. Knowing the library shortcut shows pragmatism; being able to build it shows depth.

PriorityQueue — binary heap

  • Backed by a binary heap in an array. Not sorted — only the head is guaranteed to be the min (or max with a reversed comparator).
  • O(log n) offer/poll, O(1) peek, O(n) contains/remove(arbitrary).
  • Min-heap by default. For max-heap: new PriorityQueue<>(Comparator.reverseOrder()).
  • Not thread-safe. Use PriorityBlockingQueue for concurrent use.
  • Use cases: top-K problems, Dijkstra, task scheduling, merging sorted streams, median maintenance (two heaps).

04Java Language Core — Everything You Might Be Asked

You've written Java for 20 years. But interviewers probe the corners you haven't touched since 2008 — generics erasure, the equals/hashCode contract, checked exceptions, immutability. This is the refresher.

OOP principles — the interview definitions

Encapsulation

Bundling state and behaviour, exposing only what's necessary. In Java: private fields, public methods, immutable value objects. The point is invariant protection, not just getters/setters.

Inheritance

"Is-a" relationship. Java has single class inheritance, multiple interface inheritance. Favour composition over inheritance — the classic Effective Java item, and a favourite interview probe.

Polymorphism

Same interface, different behaviour. Compile-time (overloading) vs runtime (overriding via vtable). Know the difference — "method overloading is resolved at compile time based on static types" is a real interview question.

Abstraction

Modelling the essential, hiding the incidental. Abstract classes vs interfaces — abstract classes can hold state and partial implementation; interfaces define contracts and support multiple inheritance of type.

equals, hashCode, and Comparable

The contract

  • Reflexive: x.equals(x) is true.
  • Symmetric: x.equals(y) iff y.equals(x).
  • Transitive: x=y and y=z implies x=z.
  • Consistent: repeated calls return the same result (if no state changed).
  • Null: x.equals(null) is false, never throws.
  • hashCode: equal objects must have equal hash codes.

The classic violations

  • Mutable fields in hashCode. Put the object in a HashMap, mutate it, and the lookup fails because the hash changed but the bucket didn't.
  • Overriding equals without hashCode. Two "equal" objects land in different buckets. Silent, catastrophic.
  • Inheritance breaks symmetry. Point.equals(ColorPoint) — the classic Effective Java example. Fix: prefer composition over inheritance, or use getClass() in equals rather than instanceof.

Comparable vs Comparator

  • Comparable<T> — natural ordering, compareTo. One per class.
  • Comparator<T> — external ordering, multiple possible. Use for sorting by different criteria.
  • Consistency with equals: "strongly recommended but not required". TreeMap/TreeSet use compareTo, not equals — inconsistent ordering causes subtle bugs.
  • compareTo contract: antisymmetric, transitive, consistent. Return negative/zero/positive, not -1/0/1 specifically. Use Integer.compare, not subtraction (overflow).

Generics & type erasure

The fundamental fact: generics are a compile-time concept. At runtime, List<String> and List<Integer> are both just List. The type parameter is erased.

Consequences

  • You cannot do new T(), new T[], or instanceof T.
  • You cannot overload on generic type: foo(List<String>) and foo(List<Integer>) have the same erasure and won't compile.
  • Static fields cannot use the class's type parameter.
  • Heap pollution is possible via raw types or unchecked casts.

Wildcards — PECS

Producer Extends, Consumer Super.

  • ? extends T — you can read T from it (producer). Cannot add (except null).
  • ? super T — you can write T to it (consumer). Reading gives Object.
  • ? extends T and ? super T are not interchangeable — the compiler enforces which operations are safe.
// copy src (producer) to dest (consumer)
static <T> void copy(List<? extends T> src, List<? super T> dest) {
for (T t : src) dest.add(t);
}

This is why Collections.copy has that signature. Being able to explain PECS on demand is a strong signal.

Exceptions

Checked vs unchecked

  • Checked (extends Exception, not RuntimeException) — must be declared or caught. For recoverable conditions the caller can handle.
  • Unchecked (extends RuntimeException) — programming errors, not required to declare. NullPointerException, IllegalArgumentException, IllegalStateException.
  • Error — JVM-level failures (OutOfMemoryError, StackOverflowError). Don't catch.

Best practices interviewers expect

  • Never catch and ignore. An empty catch block is a bug factory.
  • Don't catch Exception broadly unless you're at a boundary (top-level handler, batch loop).
  • Preserve the cause: throw new ServiceException("...", e), never lose the cause.
  • Use exceptions for exceptional conditions, not control flow.
  • Close resources with try-with-resources, not finally — it handles suppressed exceptions.
  • Don't log and throw. Either handle it or propagate it. Doing both produces duplicate noise.

try-with-resources and suppressed exceptions

try (var conn = dataSource.getConnection();
var stmt = conn.prepareStatement(sql)) {
...
} // both closed in reverse order; any secondary failure is "suppressed" on the primary

The finally trap

try {
return 1;
} finally {
return 2; // returns 2! Finally overrides the try return
}

Never return from finally. It silently swallows exceptions and overrides returns. This is a classic interview question.

Immutability — the recipe

  1. Make the class final (prevents subclass mutation).
  2. Make all fields private final.
  3. Defensively copy mutable inputs in the constructor and mutable outputs in getters.
  4. Don't leak this during construction.
  5. Ensure no mutable state escapes — no collections returned directly, no mutable objects reachable through getters.

Why it matters: immutable objects are inherently thread-safe, can be shared freely, make excellent map keys, and eliminate a whole class of bugs. String, Integer, and record are immutable.

The interview follow-up: "How would you make a class immutable if it holds a List?" → Return List.copyOf(list) or Collections.unmodifiableList, and copy on input.

Records, sealed types, and pattern matching

Records (Java 16+)

A transparent carrier for immutable data. Compiler generates constructor, accessors, equals, hashCode, toString.

public record Money(BigDecimal amount, Currency currency) {

Stream pipeline — the three stages

  1. Source: collection, array, generator, I/O.
  2. Intermediate ops (lazy): map, filter, flatMap, distinct, sorted, limit, skip, peek.
  3. Terminal op (triggers execution): collect, forEach, reduce, count, anyMatch, findFirst.

Nothing runs until the terminal op. This is the most commonly asked stream question.

Gotchas interviewers probe

  • Streams are single-use. Reusing a stream throws IllegalStateException.
  • Parallel streams use the common ForkJoinPool. A blocking operation in a parallel stream can starve the entire JVM's common pool. Never do I/O in a parallel stream.
  • Parallel is not automatically faster. For small collections or cheap operations, the overhead dominates. Measure.
  • Collectors.toMap throws on duplicate keys unless you provide a merge function.
  • Stateful lambdas in parallel streams produce non-deterministic results.
  • findFirst vs findAny: findFirst preserves encounter order and is more expensive in parallel; findAny is cheaper but non-deterministic.

Optional — the correct usage

  • Return type only. Not a field, not a parameter, not a collection element.
  • Never call get() without checking. Use orElse, orElseGet, orElseThrow, map, ifPresent.
  • orElse vs orElseGet: orElse evaluates the argument eagerly even if not needed — a performance trap if the default is expensive.
  • Not serializable — don't use in DTOs that cross the wire.

Collection gotchas — the ones that appear in interviews

Mutating during iteration

// WRONG — ConcurrentModificationException
for (String s : list) {
if (s.startsWith("x")) list.remove(s);
}

// RIGHT — iterator
Iterator<String> it = list.iterator();
while (it.hasNext()) {
if (it.next().startsWith("x")) it.remove();
}

// RIGHT — removeIf (Java 8+)
list.removeIf(s -> s.startsWith("x"));

Arrays.asList vs List.of

  • Arrays.asList(arr) — fixed-size view of the array. set() works, add()/remove() throw UnsupportedOperationException. Changes to the array are reflected in the list.
  • List.of(...) — truly immutable. Any mutation throws. Rejects nulls.
  • List.copyOf(coll) — immutable copy. Returns the same instance if already immutable.

subList is a view, not a copy

List<Integer> sub = list.subList(1, 4);
sub.clear(); // REMOVES those elements from the original list!

Use new ArrayList<>(list.subList(1,4)) for a copy.

Array vs ArrayList

  • Array: fixed size, covariant (Object[] o = new String[1] compiles), faster, can hold primitives.
  • ArrayList: resizable, generic (invariant), richer API, autoboxing for primitives.
  • Covariance gotcha: Object[] o = new String[1]; o[0] = 42; compiles but throws ArrayStoreException at runtime. Generics fixed this by being invariant.

HashMap iteration order

Hash-based maps have no guaranteed iteration order. If you need it, use LinkedHashMap (insertion order) or TreeMap (sorted). Relying on HashMap order is a latent bug — it can change with JDK version or capacity.

equals/hashCode in collections

HashSet and HashMap use hashCode for bucket and equals for identity. TreeSet and TreeMap use compareTo/Comparator only — a TreeSet will consider two objects equal even if equals says otherwise, if the comparator returns 0. Know this inconsistency.

06JVM & Concurrency

At your level, these questions aren't about recall — they're about whether you've ever actually debugged production. Every note below has a "what they're really asking" angle.

Memory & Garbage Collection

The generational hypothesis and heap layout

Most objects die young. The heap is split into young (Eden + two Survivor spaces) and old (tenured). Minor GCs are frequent and cheap; major/full GCs are rare and expensive.

Objects get promoted when they survive -XX:MaxTenuringThreshold collections, or immediately if they're too large for Eden (humongous allocation in G1 — anything ≥ half a region).

What they're really asking: have you tuned a real service? A good answer cites a specific symptom — e.g. "we saw 800ms p99 spikes every 40 seconds; GC logs showed repeated humongous allocations because we were building 3MB JSON strings, so we switched to streaming serialization."

Heap dumps and OOM triage — the 6-step method
  1. Confirm which OOM: Java heap space, Metaspace, GC overhead limit, unable to create native thread, or Direct buffer memory. Each has a different cause.
  2. Check the dominator tree, not the histogram. The biggest class isn't always the leak — it's whatever retains the most retained heap.
  3. Look for unbounded collections, static caches, ThreadLocal leaks in pools, and listener registrations that are never removed.
  4. Compare two dumps taken 10 minutes apart. A leak is growth in retained size over time, not absolute size.
  5. Check classloader leaks — classic in app servers with hot redeploys.
  6. Reproduce with a smaller heap (-Xmx256m) to fail fast.

Trap question: "We have OOM but the heap dump is small." → That's native memory: direct buffers, thread stacks, JNI, or Metaspace. -Xmx doesn't bound those.

Concurrency

The Java Memory Model in one page

Threads may cache values and the JIT may reorder instructions. The JMM defines happens-before so you can reason about visibility without knowing the hardware.

  • Program order: within a thread, statements appear to execute in order.
  • Monitor lock: unlock happens-before a subsequent lock on the same monitor.
  • Volatile: a write to a volatile field happens-before a subsequent read of it.
  • Thread start/join: everything before start() is visible to the new thread; everything in the thread is visible after join() returns.
  • Transitivity: if A hb B and B hb C, then A hb C.
The classic wrong answer
"I'd make the counter volatile." Volatile gives visibility, not atomicity. count++ is read-modify-write — three operations. Use AtomicInteger, LongAdder (better under contention), or a lock.

Virtual Threads — the architect-level nuance

What a strong answer includes
"Virtual threads are not a throughput silver bullet. They help when you're thread-starved on I/O. They don't help CPU-bound work, and they break if you pool them — pooling virtual threads defeats the point. We also had to replace synchronized with ReentrantLock in a shared cache to stop pinning."

Also know: Scoped Values (stable in Java 25) are the ThreadLocal replacement for virtual-thread-heavy code — they're immutable, bounded to a scope, and inherit down structured concurrency.

Transaction management — the trap questions

Why does @Transactional silently fail on a self-invocation?

Spring's default transaction management is proxy-based. When you call this.otherMethod() from inside the same bean, you bypass the proxy entirely — so no transaction advice runs. The method executes with whatever transaction context the caller had.

@Service
public class PaymentService {
public void process() {
this.save(); // ❌ no new transaction — bypasses proxy
}
@Transactional
public void save() { ... }
}

Fixes, in order of preference:

  1. Split into two beans — cleanest, and signals the design problem.
  2. Inject self via @Lazy or ApplicationContext (works, but smells).
  3. Use TransactionTemplate for programmatic control — often the right call anyway.
  4. AspectJ load-time weaving — changes proxy semantics, rarely worth it.

Architect answer: "This is really a design smell. If a method needs a different transaction boundary, it usually belongs in a different component with its own responsibility."

JPA & Hibernate performance

N+1 — detection and the three real fixes

Detect: turn on SQL logging in a test, or use a query-count assertion (Hibernate Statistics, or datasource-proxy). 1 query for orders + N for customers = N+1.

Fixes:

  • JOIN FETCH — one query. Simple, but breaks with pagination on collection fetches (Hibernate falls back to in-memory paging and warns you).
  • EntityGraph — declarative, reusable, works well with Spring Data.
  • DTO projection — best for read paths. You fetch exactly what you need and never load a managed entity you didn't want. This is the architect's default answer.
  • @BatchSize / hibernate.default_batch_fetch_size — turns N+1 into N/batch+1. Pragmatic when you can't restructure the query.
Architect framing
"We stopped treating entities as the universal read model. Write paths use entities; read paths use projections. That single decision removed most of our N+1 class of bugs."
Locking strategy in a financial system

Optimistic (@Version): read, modify, write; on conflict you get OptimisticLockException and retry. Great when conflicts are rare. Danger: retry storms under contention, and retries must be idempotent.

Pessimistic (SELECT … FOR UPDATE): serializes access. Correct under high contention, but you now hold a lock for the duration of the transaction — including any external call you foolishly made inside it. Deadlock risk if lock ordering isn't consistent.

The answer that wins points
"For balances I'd avoid both where possible by making the ledger append-only and deriving balance from entries. Then there's no hot row to lock — you're inserting, not updating. If I need a materialized balance, I use an atomic conditional UPDATE (SET balance = balance - ? WHERE balance >= ?) which is a single statement, needs no explicit lock, and fails cleanly on insufficient funds."

Auto-configuration in one paragraph

08Databases & SQL — The Complete Refresher

Databases are where most system design interviews are won or lost. Indexing, isolation, and query optimization come up in every single loop. This section is the full picture.

ACID — the definitions that matter

Atomicity

All or nothing. A transaction either fully commits or fully rolls back. Implemented via undo logs — the DB records how to reverse each change.

Consistency

The DB moves from one valid state to another. Constraints, foreign keys, and application invariants hold before and after. This is the most misunderstood — it's about invariants, not CAP consistency.

Isolation

Concurrent transactions don't interfere. The "I" is where all the interesting trade-offs live — see the isolation levels table below.

Durability

Once committed, it survives a crash. Implemented via write-ahead logging (WAL): the log is fsynced before the transaction is acknowledged.

The anomalies defined

  • Dirty read: reading uncommitted data from another transaction that may roll back. You acted on data that never officially existed.
  • Non-repeatable read: reading the same row twice and getting different values because another transaction committed in between.
  • Phantom read: running the same query twice and getting different rows because another transaction inserted/deleted matching rows.
  • Lost update: two transactions read-modify-write the same row; one overwrites the other. Prevented by optimistic locking or SELECT FOR UPDATE.
  • Write skew: two transactions each read a set, each makes a decision, both write, and the combined result violates an invariant. Serializable prevents this; lower levels do not.

MVCC — how modern databases actually do isolation

Multi-Version Concurrency Control: readers don't block writers and writers don't block readers. Instead of overwriting a row, the DB creates a new version. Each transaction sees a snapshot consistent as of its start time.

  • PostgreSQL: each row version has xmin (creating tx) and xmax (deleting tx). Visibility rules determine which version a transaction sees. Old versions are reclaimed by VACUUM — which is why PostgreSQL tables bloat and need autovacuum tuning.
  • InnoDB: undo logs + a read view. Old versions live in the undo tablespace and are purged when no transaction needs them.
  • The cost: MVCC trades space and cleanup complexity for concurrency. A long-running transaction can prevent cleanup and bloat the database — a real production issue.
  • Why it matters: "Why doesn't my SELECT block on an UPDATE?" — MVCC. This is a frequent interview question and a genuinely good thing to know.

Composite indexes and the leftmost-prefix rule

An index on (a, b, c) can be used for queries on a, (a,b), and (a,b,c) — but not on b alone or (b,c). The index is sorted by a first, then b within each a, then c.

Column order matters. Put the most selective column first, but also consider the query patterns — an index is only useful if queries can use it.

Covering index: if the index contains every column the query needs, the DB can answer from the index alone without touching the table (an "index-only scan"). Huge performance win for read-heavy queries. In PostgreSQL, use INCLUDE to add non-key columns.

-- Covering index for: SELECT name, email FROM users WHERE tenant_id = ? AND status = ?
CREATE INDEX idx_users_tenant_status
ON users (tenant_id, status) INCLUDE (name, email);
EXPLAIN — how to read a query plan

Always start with EXPLAIN ANALYZE (PostgreSQL) — it actually runs the query and shows real timings, not estimates.

What to look for:

  • Seq Scan on a large table — usually a missing index or a non-sargable predicate.
  • Nested Loop with high row estimates — often a missing index on the inner side.
  • Hash Join / Merge Join — usually fine for large joins.
  • Rows estimate vs actual — a large discrepancy means stale statistics; run ANALYZE.
  • Sort with external merge — the sort spilled to disk; increase work_mem or add an index that provides the order.
  • Buffers: shared hit vs read — reads mean disk I/O; hits mean cache.

Non-sargable predicates — the silent index killers:

-- BAD: function on the column prevents index use
WHERE DATE(created_at) = '2025-01-01'

-- GOOD: range predicate is sargable
WHERE created_at >= '2025-01-01' AND created_at < '2025-01-02'

-- BAD: leading wildcard
WHERE name LIKE '%smith'

-- BAD: implicit cast
WHERE user_id = '123' -- if user_id is int, this may prevent index use

Query optimization — the checklist

  1. Measure first. EXPLAIN ANALYZE, not guesswork.
  2. Check for missing indexes on WHERE, JOIN, and ORDER BY columns.
  3. Check for unused indexes. Every index slows writes. Drop what nothing uses.
  4. Eliminate non-sargable predicates. No functions on indexed columns.
  5. Fix N+1 at the application layer — no index will save you from 10,000 queries.
  6. Reduce rows early. Filter before joining when possible.
  7. Avoid SELECT *. Fetch only needed columns — may enable index-only scans.
  8. Watch for implicit casts that prevent index use.
  9. Consider denormalization for read-heavy paths — but only after measuring.
  10. Partition large tables by time or tenant if queries are naturally scoped.

The hard parts of sharding, which interviewers probe:

  • Cross-shard queries. Joins and aggregations become application-level operations or require a separate analytics store.
  • Cross-shard transactions. No ACID across shards. You need Saga or a two-phase approach — both have costs.
  • Resharding. Adding shards means moving data. Consistent hashing minimises it but doesn't eliminate it.
  • Hot shards. A celebrity user or a viral product can overload one shard. Detect and mitigate with sub-sharding or caching.
  • Choosing the shard key is the most consequential decision. It must distribute evenly and match your query patterns. Getting it wrong means a rewrite.

Replication

Synchronous

Primary waits for replica(s) to acknowledge before committing. Strong consistency, but writes are slower and a replica failure can block writes. Use with synchronous_commit = on and synchronous_standby_names.

Asynchronous

Primary commits immediately; replicas catch up. Fast writes, but a failover can lose the most recent transactions. This is the default and the common choice.

Replication lag

The read-after-write problem: a user writes, then reads from a replica that hasn't caught up. Fixes: read from primary for a short window after a write (read-your-writes), or use a monotonic read token, or pin the session.

Failover

Promoting a replica to primary. Split-brain is the danger — two nodes think they're primary. Fencing (STONITH), quorum, and a consensus-based coordinator (etcd, Patroni) prevent it.

TCP vs UDP — and why QUIC exists

TCP

  • Connection-oriented: 3-way handshake (SYN, SYN-ACK, ACK)
  • Reliable: acknowledgements, retransmission, ordering
  • Flow control (receiver window), congestion control (slow start, AIMD)
  • Head-of-line blocking: one lost packet stalls all streams
  • Used by: HTTP/1.1, HTTP/2, most databases, gRPC

UDP

  • Connectionless, fire-and-forget
  • No ordering, no retransmission, no flow control
  • Lower latency, lower overhead
  • Used by: DNS, video streaming, gaming, VoIP
  • You implement reliability if you need it — that's what QUIC does
QUIC and HTTP/3
QUIC runs over UDP and implements reliability, ordering, and congestion control in userspace. It eliminates TCP's head-of-line blocking (streams are independent) and combines the transport and TLS handshakes into one round trip. HTTP/3 is HTTP over QUIC. This is why HTTP/3 is faster on lossy networks — a good thing to know.

DNS — how names become IPs

  1. Browser checks its cache.
  2. OS resolver checks its cache and /etc/hosts.
  3. Query goes to the configured recursive resolver (often the ISP's or 8.8.8.8).
  4. Recursive resolver walks the hierarchy: root → TLD (.com) → authoritative nameserver for the domain.
  5. Returns the record (A, AAAA, CNAME, MX, TXT, etc.) with a TTL.

Record types you should know: A (IPv4), AAAA (IPv6), CNAME (alias), MX (mail), TXT (verification, SPF), NS (nameserver), SRV (service discovery), SOA (zone authority).

Why it matters: DNS is the first step in every request. Low TTLs enable fast failover but increase query load. DNS-based load balancing (round-robin, geo-routing) is the cheapest form of global traffic distribution — but it has no health checking unless you use a service like Route 53 health checks.

TLS — the handshake in brief

  1. Client Hello: supported cipher suites, TLS version, random nonce, SNI (server name).
  2. Server Hello: chosen cipher, certificate, server random.
  3. Key exchange: client verifies the cert against trusted CAs, then both derive a shared secret (ECDHE in modern TLS).
  4. Finished: both send a MAC over the handshake; encrypted communication begins.

TLS 1.3 improvements: 1-RTT handshake (0-RTT for resumption), removed weak ciphers, forward secrecy mandatory, encrypted SNI (with ECH). This is why TLS 1.3 is meaningfully faster.

mTLS (mutual TLS): both client and server present certificates. Standard for service-to-service auth in zero-trust architectures and service meshes.

Consensus — Raft you can whiteboard

  1. Leader election. Nodes are follower/candidate/leader. A follower times out, becomes a candidate, increments its term, and requests votes. Majority wins. Randomized timeouts prevent split votes.
  2. Log replication. Client writes to leader. Leader appends to its log and sends AppendEntries to followers. Once a majority has persisted it, the entry is committed and applied to the state machine.
  3. Safety. A candidate can only win if its log is at least as up-to-date as a majority. That's what prevents committed entries from being lost.
  4. Why it matters: a quorum of 3 tolerates 1 failure. 5 tolerates 2. Even numbers are pointless — 4 tolerates 1, same as 3, with more cost.

Kafka — the parts that trip people up

Ordering

Kafka guarantees order within a partition, not across a topic. If order matters (it usually does for money), you must key messages so related events land in the same partition — typically by account ID or transaction ID. And beware: increasing partition count changes the key→partition mapping, breaking ordering for in-flight keys.

Exactly-once

True EOS requires: idempotent producer (enable.idempotence=true) + transactional producer (transactional.id) + isolation.level=read_committed on consumers. Even then, it's exactly-once within Kafka. The moment you write to an external DB, you're back to at-least-once and need idempotent consumers.

Rebalancing

When a consumer joins/leaves, partitions are reassigned and processing stops (eager) or partially continues (cooperative, CooperativeStickyAssignor). Long processing without max.poll.interval.ms tuning causes the consumer to be kicked out — an infinite rebalance loop that looks like a hang.

Consumer lag

The single most important operational metric. Lag growing = you're producing faster than consuming. Options: add partitions + consumers (capped at partition count), batch more, or make the consumer do less work per message.

Distributed transaction patterns — the decision tree

Why 2PC fails at scale

Two-phase commit uses a coordinator: prepare → commit/abort. Problems:

  • Blocking. Participants hold locks between phases. If the coordinator dies, they block indefinitely (the "in-doubt" state).
  • Latency. Every participant must be reachable and fast; the slowest one sets the pace.
  • Availability. It's CP — a partition means the whole transaction stalls.
  • It doesn't cross trust boundaries. You cannot 2PC with an external bank.

2PC is fine inside a single database or a tightly-coupled cluster. It is not fine across microservices.

Transactional Outbox — the pattern you should default to

Problem: you write to the DB and publish to Kafka. One succeeds, the other fails. There is no transaction spanning both.

Solution: write the business row and an outbox row in the same local transaction. A separate relay (poller or CDC via Debezium) reads the outbox and publishes. Publishing becomes at-least-once; consumers must be idempotent.

BEGIN;
INSERT INTO payments(...) VALUES (...);
INSERT INTO outbox(id, aggregate_id, type, payload, created_at)
VALUES (uuid(), :paymentId, 'PaymentCreated', :json, now());
COMMIT;
-- relay reads outbox WHERE published_at IS NULL ORDER BY created_at
-- publishes, then marks published_at = now()
Why interviewers love this answer
It demonstrates you understand that distributed transactions are avoided, not solved — and that you accept at-least-once delivery as the price of not needing a global lock.

Caching is the highest-leverage performance tool and the source of the most subtle bugs. Every system design interview touches it. This is the full picture — strategies, eviction, invalidation, and the failure modes.

The failure modes — what interviewers probe

Cache stampede (thundering herd)

Many requests miss simultaneously on a hot key and all hit the DB at once. Classic after a cache restart or a popular key expires.

Fixes: request coalescing (one loader, others wait), probabilistic early expiration (refresh before TTL), or a distributed lock on the key during load.

Cache penetration

Requests for keys that don't exist — every one misses and hits the DB. Often a sign of a malicious scan or a bug.

Fixes: cache negative results (with a short TTL), bloom filter for known-missing keys, input validation.

Cache avalanche

Many keys expire at the same moment (e.g. all set with the same TTL), causing a wave of DB load.

Fix: jitter the TTL. ttl = base + random(0, base * 0.1). Simple and effective.

Stale data after a write

You write to the DB but the cache still holds the old value. The classic race: read misses, reads DB, then a write updates DB, then the read writes the stale value to cache.

Fixes: delete the cache entry on write (invalidate, don't update), use a short TTL, or use write-through. Deletion is safer than update because it's idempotent and avoids the race.

Cache hot key

One key gets disproportionate traffic (a celebrity, a trending product) and saturates a single Redis node.

Fixes: local in-process cache in front, key replication with random suffix, or sharding the hot key across nodes.

Cache and DB inconsistency

No cache strategy gives you true consistency with the DB without a transaction spanning both — which you don't have.

The honest answer: accept eventual consistency, bound the staleness with a TTL, and make the write path invalidate the cache. For read-your-writes, read from the DB for a short window after a write.

Distributed caching patterns

  • Client-side (local) cache: Caffeine, Guava. Nanosecond latency, per-instance, can become stale across instances. Use for read-mostly data with short TTLs.
  • Distributed cache: Redis, Memcached. Network hop (~0.5ms), shared across instances, consistent view. Use for shared state and larger datasets.
  • Two-tier (near cache): local cache in front of distributed cache. Best latency and reduced Redis load, but invalidation is harder. Often used for hot keys.
  • CDN: edge caching for static and cacheable content. Offloads origin entirely. Governed by Cache-Control headers and ETags.

Cache invalidation — the hard problem

Phil Karlton's famous line: "There are only two hard things in computer science: cache invalidation and naming things." Here's the practical taxonomy:

  • TTL-based: simplest. Data is stale for at most the TTL. Fine for most use cases.
  • Write-through invalidation: delete the key on write. Simple, effective, and the default recommendation for cache-aside.
  • Event-based: publish an invalidation event when data changes. Scales across services but adds a dependency and a failure mode (missed events).
  • Versioned keys: include a version in the key. Invalidate by bumping the version. Avoids the delete race entirely but requires a version lookup.
  • CDC (change data capture): read the DB's replication log and invalidate based on actual committed changes. Most accurate, most infrastructure.
The race you must mention
With cache-aside, this sequence produces stale data:
  1. Reader misses cache, reads DB (value = V1)
  2. Writer updates DB (value = V2), deletes cache
  3. Reader writes V1 to cache — stale
Mitigations: delete after write (not before), use a TTL as a backstop, or use versioned keys. Mentioning this race is a strong signal.

Kafka — the concepts you must know

Core concepts

  • Topic: named stream of records, split into partitions.
  • Partition: ordered, immutable append-only log. The unit of parallelism.
  • Offset: position within a partition. Consumers commit offsets to track progress.
  • Producer: writes records. Partitioner decides the partition (key hash or round-robin).
  • Consumer group: set of consumers that divide partitions among themselves. Each partition is consumed by exactly one consumer in a group.
  • Broker: a Kafka server. A cluster has multiple brokers; partitions are replicated.
  • Replication factor: how many brokers hold a copy. 3 is standard.
  • ISR (in-sync replicas): replicas caught up with the leader.

Producer & consumer configs that matter

  • acks=all — wait for all ISR replicas. Strongest durability.
  • enable.idempotence=true — dedupe retries at the producer.
  • max.in.flight.requests.per.connection=1..5 — with idempotence, up to 5 preserves order.
  • retries — high, with idempotence enabled.
  • compression.type=lz4 or zstd — reduce network and disk.
  • auto.commit.enable=false — commit manually after processing.
  • max.poll.interval.ms — increase if processing is slow, or you'll be kicked out.
  • isolation.level=read_committed — for exactly-once consumers.

Consumer groups and rebalancing

  • Partition assignment: each partition is assigned to exactly one consumer within a group. More consumers than partitions = idle consumers.
  • Rebalance triggers: consumer joins, consumer leaves, partition count changes, consumer heartbeat timeout.
  • Eager rebalancing: all consumers stop, revoke all partitions, rejoin. The classic "stop-the-world" of Kafka.
  • Cooperative rebalancing (CooperativeStickyAssignor): only affected partitions are revoked. Much less disruptive — use this.
  • Static membership (group.instance.id): a consumer restarts without triggering a rebalance. Useful for rolling deployments.
The infinite rebalance loop
If processing takes longer than max.poll.interval.ms, the consumer is considered dead, a rebalance is triggered, the partition is reassigned, and the same thing happens. It looks like a hang. Fix: increase the interval, or process in a separate thread, or reduce batch size.

Dead letter queues and poison messages

Poison message: a message that always fails processing — malformed, references missing data, or triggers a bug. Retrying forever blocks the queue.

The pattern: after N failed attempts, move the message to a dead letter queue (DLQ) and alert. The main queue continues processing.

// Conceptual retry + DLQ
consume(msg):
for attempt in 1..maxRetries:
try: process(msg); commit(); return
catch (RetryableException): backoff(attempt)
catch (NonRetryableException): break
dlq.send(msg, metadata: {failureReason, attempts, originalTopic})
alert.onCall()

DLQ best practices: include the original message, the failure reason, the attempt count, and the original topic/partition/offset. Provide a replay mechanism. Monitor DLQ depth as a first-class metric.

Backpressure in messaging

  • Bounded queues. Never use an unbounded queue — it converts overload into OOM. Set a capacity and decide what happens when full (block, reject, or drop).
  • Consumer lag as a signal. Kafka consumer lag is the primary saturation metric. Alert on lag growth rate, not just absolute lag.
  • Producer throttling. If the consumer can't keep up, slow the producer. This is the correct response — better than buffering indefinitely.
  • Load shedding. When the system is saturated, reject low-priority messages early with a retryable error. Honest failure beats slow failure.

The Outbox pattern — recap and implementation

-- Transaction 1: write business data + outbox event atomically
BEGIN;
INSERT INTO orders(id, user_id, amount, status) VALUES (...);
INSERT INTO outbox(id, aggregate_id, event_type, payload, created_at)
VALUES (gen_random_uuid(), :orderId, 'OrderCreated', :json, now());
COMMIT;

-- Transaction 2 (separate relay process): publish and mark
SELECT * FROM outbox WHERE published_at IS NULL ORDER BY created_at LIMIT 100;
-- for each: publish to Kafka, then:
UPDATE outbox SET published_at = now() WHERE id = :id;

Two implementations:

  • Poller: a scheduled job reads unpublished rows and publishes. Simple, but adds latency (poll interval) and DB load.
  • CDC (Debezium): reads the database replication log and publishes changes. Lower latency, no polling, but more infrastructure.

Why it's the right pattern: it makes the impossible (atomic DB + Kafka write) into two independent, idempotent operations. The cost is at-least-once delivery, which you handle with idempotent consumers.

Docker — the concepts that matter

Images vs containers

An image is a read-only template (layers). A container is a running instance with a writable layer on top. Layers are shared between images — that's why build order matters.

Dockerfile best practices

  • Use multi-stage builds — build in one stage, copy the artifact to a minimal runtime image.
  • Order layers from least to most frequently changed (dependencies before source).
  • Use a specific base image tag, not latest.
  • Run as a non-root user.
  • Use .dockerignore to keep the build context small.
  • Prefer COPY over ADD unless you need URL/tar extraction.
  • One process per container (mostly).

Why containers matter for Java

  • JVM heap sizing: pre-Java 10, the JVM ignored container limits and sized heap from host memory — leading to OOMKills. Use -XX:MaxRAMPercentage=75 and -XX:+UseContainerSupport (default in modern JDKs).
  • Startup time: JVM startup is slow for scaling. GraalVM native images or AppCDS help. This matters for serverless.
  • Image size: use JRE not JDK, alpine or distroless base, and jlink for a custom runtime.

Authentication vs Authorization

Authentication (AuthN)

"Who are you?" Verified via password, token, certificate, biometric.

  • Session-based: server stores session; client holds a cookie. Stateful, easy to revoke.
  • Token-based (JWT): stateless, signed token. Scales but hard to revoke.
  • OAuth2 / OIDC: delegated authorization + identity.
  • SAML: enterprise SSO, XML-based.
  • mTLS: both sides present certificates. Standard for service-to-service.

Authorization (AuthZ)

"What are you allowed to do?"

  • RBAC: role-based. Users → roles → permissions. Simple, most common.
  • ABAC: attribute-based. Policies over user, resource, and environment attributes. Flexible, complex.
  • ReBAC: relationship-based. Google Zanzibar-style. For complex sharing models.
  • Policy engines: OPA (Open Policy Agent), Cedar. Externalize authorization logic.

JWT — structure and pitfalls

Structure: three base64url-encoded parts separated by dots: header.payload.signature.

  • Header: algorithm and token type. {"alg":"RS256","typ":"JWT"}
  • Payload: claims — sub (subject), iss (issuer), exp (expiry), iat (issued at), aud (audience), plus custom claims.
  • Signature: HMAC (HS256) or RSA/ECDSA (RS256/ES256) over header+payload.

The critical pitfalls:

  • Never trust the payload without verifying the signature. The payload is base64, not encrypted — anyone can read it. Never put secrets in a JWT.
  • The "alg: none" attack. An attacker changes the algorithm to "none" and removes the signature. Always validate the algorithm server-side and reject "none".
  • HS256 vs RS256 confusion. With HS256, the secret is the public key. If a server expects RS256 but accepts HS256, an attacker can sign with the public key as an HMAC secret. Always pin the algorithm.
  • Revocation is hard. A JWT is valid until it expires. For immediate revocation, you need a denylist (which reintroduces state) or short expiry + refresh tokens.
  • Store tokens safely. HttpOnly, Secure, SameSite cookies for browsers. Never localStorage (XSS-accessible).

OIDC is OAuth2 + an ID token (a JWT with identity claims). Use OIDC for authentication, OAuth2 for authorization. Confusing the two is a common interview trap.

Encryption — at rest and in transit

In transit

  • TLS 1.2+ (prefer 1.3) everywhere, including internal service-to-service
  • Certificate management and rotation (Let's Encrypt, ACME, cert-manager)
  • HSTS to prevent downgrade attacks
  • mTLS for zero-trust internal communication

At rest

  • Full-disk encryption (EBS, RDS) — protects against physical theft
  • Application-level encryption — protects against DB compromise. Encrypt sensitive fields (PII, PAN) with a KMS-managed key.
  • Key rotation policies
  • Envelope encryption: data key encrypted by a master key

Secrets management

  • Never in code or config files. Not even in private repos.
  • Environment variables are better but still visible in process listings and crash dumps.
  • Dedicated secret stores: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager. Support rotation, audit, and fine-grained access.
  • Kubernetes: Secrets are base64 by default — use External Secrets Operator, Sealed Secrets, or a CSI driver that mounts secrets from a vault.
  • Rotation: automate it. A secret that's never rotated is a secret that will eventually leak.
  • Audit: log every access to a secret. Who read what, when.

The security questions architects get asked

How do you secure service-to-service communication?

"Three layers. First, mTLS for transport — every service has a certificate, and both sides verify. In Kubernetes, a service mesh (Istio, Linkerd) handles this without application changes. Second, short-lived credentials or tokens for authorization — I'd use SPIFFE/SPIRE for workload identity, or your cloud provider's IAM roles. Third, network segmentation — services should only be able to reach what they need, enforced by security groups or network policies. The principle throughout is zero-trust: never assume the internal network is safe."

How do you handle PII in a payment system?

"The first rule is don't store what you don't need. For PCI, that means card data never touches our servers — tokenize at the edge with the PSP's SDK. What we do store is encrypted with a KMS-managed key, and access is logged. Logs are scrubbed of PII at the logging library level, not by a post-processing job, because a post-processing job can fail. For data at rest, I'd use column-level encryption for sensitive fields so a database compromise doesn't expose them. For data in use — the hardest case — I'd look at tokenization or format-preserving encryption if analytics needs to work with the data."

How do you prevent SQL injection?

"Parameterized queries, always. PreparedStatement in JDBC, or the equivalent in JPA. Never string concatenation, never String.format into a query, never dynamic table names from user input. If you genuinely need dynamic SQL — for example a reporting tool — the column and table names must come from an allowlist, not from user input. I'd also add a static analysis rule that fails the build on string concatenation into a query, because this is a class of bug that should be impossible to introduce."

Domain-Driven Design — the concepts that matter

Strategic DDD

  • Bounded context: an explicit boundary within which a domain model is defined and consistent. The key decomposition tool.
  • Ubiquitous language: shared vocabulary between developers and domain experts within a bounded context.
  • Context map: how bounded contexts relate — shared kernel, customer/supplier, conformist, anticorruption layer.
  • Core domain: where your competitive advantage lives. Invest here.
  • Supporting / generic subdomains: necessary but not differentiating. Buy or outsource where possible.

Tactical DDD

  • Entity: has identity that persists across state changes.
  • Value object: immutable, defined by attributes. Money, Address.
  • Aggregate: cluster of entities and value objects with a single root. The consistency boundary.
  • Aggregate root: the only entry point to the aggregate. All invariants enforced here.
  • Repository: persistence abstraction for aggregates.
  • Domain event: something meaningful that happened. PaymentCaptured.
  • Domain service: logic that doesn't belong to a single entity.

The aggregate design rule: keep aggregates small. One aggregate = one transaction. If you need to modify two aggregates atomically, you probably have the boundaries wrong, or you need eventual consistency between them.

Decomposition strategies

  • By business capability: Payments, Fraud, Accounts, Notifications. Aligns with how the business thinks.
  • By bounded context (DDD): each context has its own model and language. The most robust approach.
  • By subdomain type: core, supporting, generic. Different investment levels.
  • By scaling characteristics: read-heavy vs write-heavy, latency-sensitive vs batch.
  • By team (Conway's Law): the system will mirror your communication structure. Use the inverse Conway manoeuvre — design teams to produce the architecture you want.
  • By transaction boundary: things that must be atomic together belong together. This is the constraint that most often overrides the others.

The patterns you must know

API Gateway

What: a single entry point for clients, routing to backend services.

Responsibilities: routing, authentication, rate limiting, request/response transformation, protocol translation, caching, observability.

Trade-off: it's a potential bottleneck and a single point of failure. Keep it thin — business logic belongs in services. For BFF (Backend for Frontend), one gateway per client type (web, mobile) so each gets an optimized API.

Service Discovery

Problem: service instances are ephemeral — they come and go, IPs change.

Client-side discovery: the client queries a registry (Eureka, Consul) and picks an instance. More control, but discovery logic in every client.

Server-side discovery: the client calls a load balancer, which queries the registry. Simpler clients, one more hop.

Kubernetes: built-in — Services provide stable DNS names and virtual IPs. You rarely need a separate registry.

CQRS (Command Query Responsibility Segregation)

What: separate the write model from the read model. Writes go to a normalized, transaction-safe store. Reads come from a denormalized, query-optimized store, kept in sync via events.

Why: read and write workloads have different requirements. A single model optimized for both is optimized for neither.

Trade-off: eventual consistency between the two models, more infrastructure, more complexity. The read model must handle stale data — which is often fine (feeds, dashboards) and sometimes not (balance checks).

When to use: read-heavy systems with complex queries, or where the write model is naturally different from what the UI needs. Not a default.

Event Sourcing

What: store the sequence of events that caused the current state, not the current state itself. Current state is derived by replaying events.

Benefits: complete audit trail (built-in, not bolted on), ability to replay to any point in time, ability to project new read models from history, natural fit for event-driven systems.

Costs: event schema evolution is hard (you can never change old events), replay can be slow, snapshots are needed for performance, eventual consistency, and the mental model is unfamiliar.

Use when: audit is a first-class requirement (finance, healthcare), or you need temporal queries ("what did this look like last month?").

Event Sourcing vs Event-Driven
These are different. Event-driven means services communicate via events. Event sourcing means events are the source of truth for state. You can have one without the other. Interviewers frequently conflate them — being precise is a strong signal.
Strangler Fig (for modernization)

What: incrementally replace a legacy system by routing traffic to new implementations piece by piece, until the old system can be decommissioned.

How: put a facade (proxy/gateway) in front of the legacy system. Implement new functionality in the new system. Route traffic gradually. Repeat until the legacy system has no traffic.

Why it works: no big-bang rewrite (which almost always fails), continuous delivery of value, ability to roll back individual pieces, and the legacy system keeps working throughout.

The hard part: the data. You'll have a period where data lives in both systems. Need a sync mechanism (CDC, dual-write with reconciliation) and a plan for the cutover.

Sidecar, Ambassador, and Service Mesh

Sidecar: a helper process deployed alongside the main service, sharing network and lifecycle. Handles cross-cutting concerns (logging, proxying, config) without changing the application.

Ambassador: a sidecar that proxies outbound traffic — handles retries, circuit breaking, observability for outgoing calls.

Service mesh: a fleet of sidecars (or eBPF-based agents) managed centrally, providing mTLS, traffic management, observability, and policy enforcement without application code. Istio, Linkerd, Consul Connect.

Trade-off: adds latency, operational complexity, and a new thing to debug. Justified at scale; overkill for a handful of services.

What "good tests" means at architect level

  • Fast. The unit suite should run in seconds. If it doesn't, developers stop running it.
  • Deterministic. No flakiness. A flaky test is worse than no test — it trains people to ignore failures.
  • Independent. No test depends on another's state or execution order.
  • Testing behaviour, not implementation. If refactoring breaks tests, they were testing the wrong thing.
  • Readable. Given/When/Then or Arrange/Act/Assert. A test should read as a specification.
  • Fast feedback. Fail with a message that tells you what's wrong, not just that something is.
The mocking trap
If a test needs 15 mocks, the class under test has too many dependencies. Excessive mocking is a design smell, not a testing strategy. The fix is to refactor the production code, not to write more elaborate test setup.

TDD — the honest version

The cycle: Red (write a failing test) → Green (make it pass, simply) → Refactor (clean up with tests as a safety net).

What it's actually good for: driving design (if it's hard to test, the design is probably wrong), ensuring test coverage, and catching regressions.

Where it's impractical: exploratory work where you don't know the interface yet, UI work, and spike/prototype code. Pretending otherwise is dogma, not engineering.

The architect answer: "I use TDD where the design is reasonably clear and the behaviour is specifiable. For exploratory work, I write tests after the shape emerges. The constant is that everything that ships has tests — the order is a tool, not a religion."

Observability — the three pillars

Metrics

Numeric measurements over time. Cheap, aggregatable, good for alerting.

  • RED method (services): Rate, Errors, Duration
  • USE method (resources): Utilization, Saturation, Errors
  • Four golden signals: latency, traffic, errors, saturation
  • Tools: Prometheus, Grafana, Micrometer, CloudWatch

Logs

Discrete events with context. Expensive, detailed, good for debugging.

  • Structured (JSON), not free text
  • Correlated by trace ID and request ID
  • Levelled — ERROR means a human should look
  • No PII — never log card numbers, passwords, tokens
  • Tools: ELK, Loki, Splunk, CloudWatch Logs

Traces

The path of a request across services. Essential for distributed systems.

  • Trace ID propagated in headers (W3C traceparent)
  • Spans for each operation, with timing and metadata
  • Sampling — you can't trace everything; sample intelligently (always trace errors and slow requests)
  • Tools: Jaeger, Tempo, Zipkin, X-Ray, Datadog

OpenTelemetry

The emerging standard. One API/SDK for metrics, logs, and traces. Vendor-neutral — you can change backends without changing instrumentation. Use the Java agent for auto-instrumentation of common libraries (Spring, JDBC, Kafka, HTTP clients), plus manual spans for business operations.

Alerting — what good looks like

  • Alert on symptoms, not causes. "Users are seeing errors" not "CPU is high."
  • Every alert must be actionable. If the on-call can't do anything, it's not an alert — it's a dashboard.
  • Page on burn rate, not raw thresholds. "The error budget will be exhausted in 2 hours at the current rate" is more useful than "error rate > 1%."
  • Reduce noise ruthlessly. Alert fatigue is real. An on-call who's paged 20 times a night stops responding thoughtfully.
  • Blameless post-mortems. Focus on systemic causes, not individuals. The goal is learning, not punishment.

17The System Design Answer Framework

A 45-minute design interview is not a test of what you know. It's a test of how you think under observation. This framework keeps you structured and visibly rigorous.

The 6 phases (with time budgets for a 45-min round)

  1. Clarify & scope — 5 min. Never draw anything yet. Ask about scale, latency, consistency, failure tolerance, and what's explicitly out of scope.
  2. Back-of-envelope — 4 min. QPS, storage/year, read:write ratio, bandwidth. Round aggressively. This tells you whether you need one box or a thousand.
  3. API contract — 4 min. 4–6 endpoints or events. This forces precision about what the system actually does.
  4. High-level design — 10 min. Boxes and arrows. Data flow, not deployment topology.
  5. Deep dive — 15 min. Pick the 2 hardest components and go deep. This is where you win.
  6. Failure modes & trade-offs — 7 min. What breaks, what you'd monitor, what you'd do differently with more time.

The clarifying questions that make you sound like an architect

Scale & shape

  • How many users / transactions per day, and what's peak vs. average?
  • What's the read:write ratio?
  • Is traffic global or single-region? Does data need to stay in-region?
  • What's the expected growth over 2 years?

Correctness & cost

  • What happens if two users act on the same record simultaneously?
  • Is eventual consistency acceptable anywhere, or is everything money-critical?
  • What's the cost of a duplicate vs. the cost of a loss?
  • What's the latency SLA — p50 and p99?
The single most common senior-candidate mistake
Diving into architecture in the first 60 seconds. Interviewers read this as "can't handle ambiguity — will build the wrong thing confidently." Even if you're certain, ask two questions and state your assumptions out loud: "I'll assume 5,000 TPS peak, strong consistency on the ledger, eventual on the read model, and single-region for now — correct me if that's off."

Phrases that signal architect-level thinking

  • "Before I design, let me confirm what we're optimising for."
  • "There are two viable approaches here. Let me give you the trade-off and my recommendation."
  • "This is the part I'd prototype first, because it's where the risk concentrates."
  • "I'm choosing X, and the price I'm paying for that is Y."
  • "If this fails at 3am, here's what the on-call engineer sees and what they'd do."
  • "That's a build-vs-buy call. My instinct is buy, because this isn't our differentiator."
  • "I'd want an ADR for this decision so the reasoning survives us."

18Fintech System Design: The Six Constraints

Fintech interviews are not generic system design with different nouns. The scoring rubric changes. Scaling to a billion users is a nice-to-have; not losing money is mandatory. Memorize these six constraints and lead with them — it immediately signals domain fluency.

Open every fintech design with this
"Money can never be lost, duplicated, or created. That single constraint dictates every design choice below. It means idempotency is not optional, the ledger write must be strongly consistent, and I need a reconciliation process because I will not be able to guarantee atomicity with external systems."

Constraint 1 — Idempotency

The problem: networks time out. Clients retry. Users double-tap. A payment that succeeded server-side but timed out client-side will be retried, and without protection, charged twice.

The design: the client generates a UUID idempotencyKey per logical payment attempt (not per HTTP request). The server, before any downstream call, attempts an atomic insert into an idempotency table with a unique constraint on the key.

INSERT INTO idempotency_keys (key, request_hash, status, response, created_at)
VALUES (:key, :hash, 'IN_PROGRESS', NULL, now())
ON CONFLICT (key) DO NOTHING;
-- 0 rows affected → key exists → return stored response or 409 IN_PROGRESS

The subtleties interviewers probe:

  • Key reuse with different payloads. Store a hash of the request body. Same key + different body = 422, not a silent wrong response. This is a real Stripe behaviour.
  • Concurrent duplicates. Two requests with the same key arrive simultaneously. The unique constraint means one wins; the other must either wait or return "in progress". A naive check-then-insert has a race.
  • Key retention. How long do you keep keys? Too short and a late retry double-charges; too long and the table grows forever. Typical: 24–72 hours for API keys, longer for settlement-critical flows. Partition the table by time and drop old partitions.
  • Partial failure. Key marked IN_PROGRESS but the process died. You need a sweeper that resolves stale in-progress keys by querying the downstream for actual state — never by assuming.
The answer that fails
"I'd check if the transaction exists, and if not, create it." That's a check-then-act race. Two concurrent requests both see "not exists" and both create. You must rely on a database uniqueness constraint, not application logic.

Constraint 2 — Consistency: strong where it counts, eventual where it doesn't

The mistake: treating "the system" as having one consistency model. Real fintech systems have several, deliberately layered.

DataModelWhy
Ledger entries / balance debitLinearizable Money correctness. Cannot read stale balance before a debit.
Idempotency key lookupLinearizable A stale read means a duplicate charge.
Fraud decision cacheEventual (seconds) Best-effort signal; a slightly stale score is acceptable, blocking everything is not.
Transaction history shown in appEventual (~200ms) Read from a replica/CQRS view. Nobody's money depends on it.
Analytics / reportingEventual (hours) Batch/warehouse. Fine.

Interviewer follow-up you should pre-empt: "How do you stop the app showing a stale balance right after a payment?" → Read-your-writes. After a successful write, pin that user's session to the primary (or to the write-through cache) for N seconds, or return the authoritative balance in the payment response so the client doesn't need to re-read.

Constraint 3 — Downstream rate limits are your real ceiling

Your service can autoscale to 10,000 pods. The bank's payment gateway will still accept 1,000 TPS. Autoscaling your API past that point doesn't increase throughput — it just converts your pods into threads blocked on a rate-limited dependency, and then into a queue that grows until you OOM.

The design:

  • Decouple sync from async. The API validates, checks idempotency, enqueues, and returns 202 Accepted with a transaction ID. The client polls or receives a webhook.
  • Queue as a shock absorber. Kafka or SQS in front of the downstream call. Size it for your peak burst, and monitor queue depth as your primary saturation signal.
  • Rate-limit the consumer, not the producer. The consumer drains at exactly the downstream's permitted rate. Use a token bucket shared across instances (Redis-backed) if the limit is global.
  • Reject early when the queue is full. Returning a fast 503 with Retry-After is honest and recoverable. Silently queueing past your capacity is not — it converts a spike into an outage that lasts hours after traffic normalises.
Say this
"The bottleneck is outside my boundary, so autoscaling is the wrong lever. My levers are queue depth, consumer concurrency matched to the downstream's limit, and honest backpressure to the client."

Constraint 4 — Retry storms and the thundering herd

How 10× becomes 30×: downstream slows → clients time out at 2s → clients retry → each retry adds load → downstream slows further → more timeouts. A modest spike becomes a self-sustaining outage.

The defences (name all four):

  1. Idempotency — so retries are safe and therefore bounded.
  2. Exponential backoff with full jitter. sleep = random(0, min(cap, base * 2^attempt)). Jitter is the part people forget — without it, all clients retry in lockstep.
  3. Circuit breaker. After N consecutive failures, stop calling for a cooldown. Fail fast rather than pile up doomed requests.
  4. Retry budgets. Cap retries as a percentage of total traffic (e.g. 10%). Once the budget is exhausted, stop retrying entirely. This is how Google SRE does it.

Also: only retry idempotent operations, and only on retryable errors (timeouts, 5xx, 429). Never retry a 400 or a hard decline.

Constraint 5 — Reconciliation

Accept this upfront: your system and the bank's system will disagree. Network partitions, timeouts at the exact moment of commit, clock skew, and human error guarantee it. The question is not whether you'll be inconsistent — it's whether you'll detect and correct it.

The design:

  • Daily settlement file from each counterparty (bank, card network, PSP).
  • Matching engine that joins your records to theirs on their transaction reference.
  • Break categories: MISSING_IN_THEIRS, MISSING_IN_OURS, AMOUNT_MISMATCH, STATUS_MISMATCH, DUPLICATE.
  • Automated resolution for known patterns (e.g. a timeout-then-success resolves to SUCCESS). Manual queue with an SLA for everything else — and an audit trail of every adjustment.
  • Never silently mutate a ledger entry. Corrections are new compensating entries.

Interview gold: mentioning reconciliation unprompted is one of the strongest signals you've actually worked in payments. Most candidates never bring it up.

Constraint 6 — Auditability, immutability, and money representation

Ledger & audit

  • Append-only journal. You never UPDATE a financial record. Corrections are new compensating entries.
  • Double-entry. Every transaction has debits and credits that sum to zero. This gives you free integrity checking: if the books don't balance, you have a bug.
  • Audit trail on every state change: who, what, when, from what, to what, under which request ID.
  • Immutability enables replay. You can rebuild any derived state (balances, views) from the journal. This is enormously valuable for debugging and for regulatory response.
  • Retention: financial records often have 7-year retention requirements. Plan storage accordingly.

Money representation

  • Never double or float. 0.1 + 0.2 != 0.3. This is the fastest way to fail a fintech interview.
  • Store minor units as integers (cents, paise) — simplest and fastest.
  • Or BigDecimal with explicit scale and RoundingMode.HALF_EVEN (banker's rounding) where required.
  • Currency is part of the amount. Money should be a value object of (amount, currency) — never a bare number. Mixing currencies is a category error.
  • Rounding must be deliberate. FX conversion, tax, and interest all round — and the rounding difference has to land somewhere. Usually a dedicated rounding/suspense account.
Also know (bonus signals)
PCI-DSS: never store PAN or CVV; tokenize at the edge; the card data should never touch your application servers. PSD2/SCA: strong customer authentication for EU payments. Idempotency + PII: don't log request bodies containing account numbers — hash them.

Case 1 — UPI-style payment spike: 10× traffic, PSP can't scale

Prompt: "During a flash sale, transaction volume goes from 1,000 to 10,000 TPS in 90 seconds. Your bank PSP is contractually capped at 1,200 TPS and cannot be raised. Design the system so we don't lose transactions or fall over."

My clarifying questions

  • Is the cap global or per-merchant/per-BIN?
  • What's the acceptable latency for the user to see a final status — 2 seconds or 2 minutes?
  • Can we shed load by rejecting with a retryable error, or must we accept everything?
  • Is the spike predictable (a scheduled sale) or genuinely sudden?

Model answer

"The core insight is that the PSP is the bottleneck and it's outside my control, so autoscaling my API is the wrong lever — it just moves the queue from my pods to my heap. I'd decouple the synchronous user-facing path from the asynchronous PSP call.

Ingest path: the API does four things and nothing else — authenticate, validate, write the idempotency key (atomic insert with unique constraint), and enqueue. Then it returns 202 Accepted with a transaction ID. That's a sub-50ms operation with no downstream dependency, so it stays fast under any load.

The queue: Kafka with partitions keyed by account ID so that all of one user's transactions stay ordered. I'd size the topic to absorb roughly 10 minutes of peak — about 6 million messages at 10K TPS. Retention of 24 hours gives me replay capability if the consumer has a bug.

The consumer: drains at exactly 1,200 TPS using a Redis-backed token bucket shared across instances, so the limit is global, not per-pod. Concurrency is tuned to the PSP's latency — if the PSP takes 200ms, I need roughly 240 in-flight requests to sustain 1,200 TPS. I'd set a hard timeout at 3 seconds with a circuit breaker, because a slow PSP is worse than a failed one.

Backpressure: this is the part that decides whether we survive. I'd monitor queue depth and consumer lag as the primary saturation signals. When the queue exceeds a threshold — say 15 minutes of drain capacity — I stop accepting new work and return 503 with Retry-After. That's honest: the user can retry in 30 seconds. The alternative, queueing indefinitely, means a user waits four minutes for a payment that then fails, and we've converted a spike into a multi-hour outage.

Client contract: the app polls GET /transactions/{id} with backoff, or better, receives a webhook or push notification. Either way the user sees 'Processing' immediately rather than a spinner.

Reconciliation: any transaction that times out at the PSP goes into an UNKNOWN state. It is never assumed failed and never assumed successful. A sweeper queries the PSP for status, and the daily settlement file catches anything the sweeper missed.

Cost of this design: users get a delayed final status instead of an immediate one, and I've added Kafka as a critical dependency. I'd mitigate the second by making Kafka multi-AZ with replication factor 3 and min.insync.replicas=2."

Follow-ups to expect

  • "The queue is full. What exactly do you return, and how do you avoid a retry storm?" → 503 with Retry-After and jitter; clients back off; idempotency keys make retries safe.
  • "Kafka goes down. Now what?" → Bounded local fallback is dangerous. Better: fail closed for new payments (return 503) rather than accept work you cannot durably store. Accepting and dropping is the worst outcome.
  • "How do you test this before the sale?" → Load test at 3× expected peak, chaos-test the PSP with injected latency and 5xx, verify the circuit breaker and queue drain behaviour.
Case 2 — Double debit: user timed out, retried, got charged twice

Prompt: "A user's payment request times out on the client but succeeds on the backend. They retry. How do you prevent a double debit — and how do you fix it if it already happened?"

Model answer

"Prevention has to happen before any money movement, and it has to be enforced by the database, not by application logic — because application logic has a race condition.

The idempotency key. The client generates a UUID once per logical payment attempt and sends it in a header. Critically, it's generated once per attempt, not per HTTP request — so the retry carries the same key.

The atomic claim. The very first thing the server does is attempt an insert into an idempotency table with a unique index on the key. If the insert succeeds, this request owns the operation. If it fails on the unique constraint, a duplicate exists and we handle it from the stored record. No check-then-act, no race.

The three states. The record moves through IN_PROGRESS → SUCCEEDED or FAILED. On a duplicate request:

  • SUCCEEDED → return the exact stored response, including the same transaction ID. The client cannot tell it was a replay, which is the point.
  • FAILED → return the stored failure, or allow a new attempt with a new key.
  • IN_PROGRESS → return 409 with Retry-After. Do not start a second attempt. This is the case that people get wrong.

Payload integrity. I'd store a hash of the request body alongside the key. Same key with a different body returns 422 — otherwise a client bug could silently return the wrong transaction's result.

Stale IN_PROGRESS records. If the process dies mid-flight, the key is stuck. A sweeper finds records older than a threshold and resolves them by querying the PSP for the actual status — never by assuming success or failure. This is the reconciliation hook.

Retention. Keys live 24–72 hours for API clients, longer for settlement flows. I'd partition the table by day and drop old partitions rather than deleting rows, which would bloat the table and the indexes.

If it already happened: the corrective action is not to delete the extra debit — financial records are append-only. You post a compensating credit entry, linked to the original transaction ID with a reason code, and notify the customer. The audit trail shows the full story: original debit, erroneous second debit, reversal. Anyone reviewing it later can reconstruct exactly what happened and why.

Detection: a daily job that flags any account with two debits for the same merchant and amount within a short window. That's a heuristic, not proof, so it goes to a human queue — but it catches the cases idempotency missed, like a client that generated two different keys."

Follow-ups

  • "What if the client doesn't send a key?" → Some APIs synthesize one from a hash of the request body plus user ID plus a time bucket. It's weaker — legitimate identical payments get deduped — so I'd only do it for low-value operations, and require explicit keys for money movement.
  • "Two requests with the same key arrive 5ms apart on different pods?" → The unique constraint on the database handles it. One insert wins, the other gets a constraint violation. This is exactly why I don't do a SELECT first.
Case 3 — Payment success rate dropped 3% after a deploy. No alerts fired.

Prompt: "Your payment success rate dropped from 97% to 94% after yesterday's deploy. No alerts fired. Root-cause it."

Model answer

"First, the fact that no alerts fired is itself the primary finding. Our alerting is measuring infrastructure health — CPU, memory, error rates on 5xx — and a 3% success-rate drop doesn't move any of those needles. A payment that gets declined looks like a perfectly healthy HTTP 200. So I'd treat this as two problems: restore the success rate, and fix the observability gap.

Triage order:

  1. Confirm the drop is real and correlated with the deploy. Pull success rate by hour for the last 7 days. If it stepped down at the deploy timestamp, that's strong evidence. If it's a gradual slope, it's probably not the deploy.
  2. Segment before theorising. Split by PSP, by issuer/BIN, by card type, by geography, by API version, by amount band. A 3% overall drop is usually a much larger drop in one narrow segment. This is the single highest-value step — it usually hands you the answer.
  3. Compare error codes. Declines vs. technical failures are completely different problems. A rise in technical failures (timeouts, 5xx from the PSP, connection resets) points at the integration. A rise in declines points at data or fraud rules.
  4. Check the diff for the usual suspects. Timeout values changed? Retry logic changed? Header or field added? TLS/cipher config? Connection pool size? New validation that's rejecting valid edge cases? A new library version changing serialization?
  5. Canary compare. If you still have a canary or a previous version running, compare its success rate in the same time window. That isolates deploy vs. external.

The most likely culprits in my experience:

  • A timeout reduced — a 5s timeout dropped to 2s turns slow-but-successful authorizations into failures. This is extremely common and completely invisible in error rates.
  • A retry removed or broken — transient network blips that used to be retried now surface as failures.
  • Connection pool sizing changed, causing queuing that pushes latency past the timeout under peak only — so it looks fine in staging.
  • A new validation rule rejecting a valid edge case: cards with unusual formatting, non-ASCII names, unusual address formats, zero-decimal currencies like JPY.
  • Serialization change — a field renamed or a null now omitted, causing the PSP to reject a request that used to be valid.

Immediate mitigation: roll back. Don't debug in production while customers are failing payments. Once stable, reproduce in staging with production-shaped traffic.

The observability fix, which I'd argue is the more important deliverable:

  • Alert on business metrics, not just infrastructure. Payment success rate by PSP and by card network, with a threshold like "<96% over 15 minutes". This is a burn-rate alert on an SLO.
  • Alert on p99 latency per dependency, not just error rate. Slow is the leading indicator; errors are the lagging one.
  • Track timeout occurrences as a first-class metric. They currently vanish into a generic error bucket, which is why this was invisible.
  • Automated canary analysis. Compare the new version's success rate against the baseline as part of the deploy pipeline and auto-rollback on a statistically significant drop.
  • Structured decline reasons end-to-end — PSP code, mapped to our taxonomy, with the raw code preserved for support.

The meta-point I'd make to the interviewer: a 3% drop in a payments system is a revenue event measured in real money per hour, and our alerting didn't see it because we were monitoring the machines instead of the business. That's the lesson."

Case 4 — Design a ledger for a multi-currency wallet

Prompt: "Design the data model and core operations for a wallet that holds balances in multiple currencies and supports transfers, top-ups, and withdrawals."

Model answer

"I'd model this as an append-only double-entry ledger. The wallet balance is a derived value, not a stored source of truth. That's the foundational decision — everything else follows from it.

Schema

accounts(
id uuid PK,
owner_id uuid,
account_type enum(USER_WALLET, FEE_INCOME, PSP_SUSPENSE, FX_ROUNDING, ...),
currency char(3), -- ISO 4217
created_at timestamptz
)

journal_entries( -- one row per financial event
id uuid PK,
idempotency_key text UNIQUE,
event_type text,
occurred_at timestamptz,
metadata jsonb -- correlation, actor, channel
)

postings( -- the double-entry lines
id bigserial PK,
entry_id uuid FK -> journal_entries,
account_id uuid FK -> accounts,
amount_minor bigint, -- signed; debit negative, credit positive
currency char(3),
created_at timestamptz
)

-- INVARIANT: for every entry_id, SUM(amount_minor) = 0

Why these choices:

  • Integer minor units. No floating point anywhere near money. bigint handles far more than we'll ever need.
  • Signed amounts. Debits negative, credits positive. The zero-sum invariant becomes a single SUM() check — cheap and continuous.
  • Currency on the account, not the posting. An account holds exactly one currency; currency conversion is modelled as two postings in different accounts plus an FX account capturing the spread and rounding. This makes FX gains/losses explicit rather than hidden.
  • Append-only. No UPDATE, no DELETE, ever. Corrections are new entries. This gives us a complete audit trail for free and makes the ledger replayable.

Core operations

Transfer 100 USD from Alice to Bob: one journal entry, two postings — Alice's wallet −10000, Bob's wallet +10000. Same currency, same entry, sums to zero.

Top-up from a card: entry with a debit to PSP_SUSPENSE and a credit to the user's wallet. The suspense account represents money in flight; it's cleared when settlement confirms.

FX: four postings — debit Alice's USD wallet, credit the USD FX pool, debit the EUR FX pool, credit Bob's EUR wallet, plus a rounding posting to the FX_ROUNDING account for the fractional difference. Every entry still sums to zero in its own currency.

Balance computation

Two options, and I'd use both:

  • On demand: SELECT SUM(amount_minor) FROM postings WHERE account_id = ?. Correct, but slow as history grows.
  • Materialised balance maintained in the same transaction as the postings, with a periodic job that recomputes from the journal and alerts on any discrepancy. The journal is the source of truth; the balance is a cache.

Preventing overdraft without a hot row lock

Instead of SELECT ... FOR UPDATE on the balance row — which serialises all of a user's transactions and creates a hotspot — I'd use a conditional update:

UPDATE balances
SET amount_minor = amount_minor - :amt, version = version + 1
WHERE account_id = :id AND amount_minor >= :amt;
-- 0 rows updated → insufficient funds → abort the whole entry

This is atomic, needs no explicit lock, and fails cleanly. Under extreme contention you'd still serialise on that row, but for a single user's wallet that's acceptable — one user isn't generating thousands of concurrent transactions.

Scale & operations

  • Partition postings by month on created_at. Retention policies and archival become trivial, and old partitions can be read-only.
  • Read replicas serve statements and history. Never for balance checks that gate a spend.
  • Continuous integrity check: a job that verifies every entry sums to zero across the last N hours, and that materialised balances match journal sums. Alert on any violation — that's a P1, because it means a code path is writing bad data.
  • Statement generation reads from the journal, not from a mutable balance, so a statement is reproducible years later.

The trade-off I'm accepting: deriving balances is more expensive than reading a single row, and the schema is more complex than a simple balance column. I'm paying that cost because auditability and correctness are non-negotiable in this domain, and because 'why is my balance wrong' is a question you want to be able to answer definitively."

Case 5 — Cross-border payment with FX and compliance

Prompt: "Design a system that lets a user in the US send money to a recipient in India, arriving in INR."

Model answer

"Cross-border is where payments stop being a technical problem and become a coordination problem. There are at least four independent systems involved — our ledger, an FX liquidity provider, a correspondent banking rail, and a local payout partner in India — and I cannot make them atomic. So the design is fundamentally a state machine plus reconciliation.

Clarifying questions I'd ask

  • Is the FX rate locked at quote time or at execution time? Who bears the rate risk in between?
  • What's the acceptable delivery time — minutes, hours, or T+1?
  • Who are the payout partners in India, and what's their API?
  • What compliance obligations apply — KYC, AML, sanctions screening, purpose codes?
  • What's the value range? A $50 remittance and a $5M corporate payment are different systems.

Flow

  1. Quote. User requests a quote. We lock a rate for 30 seconds with a rate-lock ID. The rate includes our spread. The quote is a promise with a real financial exposure — if the market moves against us in those 30 seconds, we eat it.
  2. Compliance gate. Before any money moves: KYC on the sender, sanctions screening on both parties, AML transaction monitoring, and — for India — purpose codes and FEMA compliance. This must be a synchronous gate with an async fallback for manual review. Failures here are not errors; they're business outcomes.
  3. Funds capture. Debit the sender's USD wallet via the ledger. The money is now in a suspense account, not yet sent.
  4. FX execution. Call the liquidity provider to convert USD → INR at or near the locked rate. Record the actual rate obtained.
  5. Payout instruction. Send INR to the local partner for delivery to the recipient's bank account (via UPI, IMPS, or NEFT depending on amount and speed).
  6. Settlement & reconciliation. The partner confirms delivery. We clear the suspense account and post the final ledger entries.

The state machine — and why it's the heart of the answer

QUOTED → COMPLIANCE_PENDING → COMPLIANCE_APPROVED
→ FUNDS_HELD → FX_EXECUTED → PAYOUT_INITIATED
→ PAYOUT_CONFIRMED → SETTLED

Terminal/exception: COMPLIANCE_REJECTED, FX_FAILED,
PAYOUT_FAILED, REFUNDED, IN_MANUAL_REVIEW

Every transition is persisted, idempotent, and emits an event. The transfer ID is the idempotency key threaded through every external call. If we crash at any point, a recovery job reads the state and resumes — or compensates.

Compensations

  • FX executed but payout failed: we're holding INR we don't need. Retry with a different partner; if that fails, convert back (accepting the round-trip FX loss) and refund. The loss is a cost of doing business and must be modelled, not hidden.
  • Funds held but compliance rejected: refund the sender. Straightforward.
  • Payout initiated but no confirmation: this is the dangerous one. Never assume failure and never assume success. Query the partner, and if unresolved, escalate to manual review. A duplicate payout is a real financial loss.

The hard parts I'd call out explicitly

  • Rate risk. The window between quote and execution is uncompensated exposure. Mitigations: short lock windows, hedging the aggregate position, or passing the risk to the user with a rate that refreshes at execution. This is a business decision as much as a technical one, and I'd want to know which the business has chosen.
  • Partial information. The partner's API will sometimes return "pending" forever. You need an SLA-based escalation: after N hours, a human investigates.
  • Regulatory variance. Rules differ by corridor and change. I'd model compliance as a pluggable rules engine per corridor rather than hardcoding logic — otherwise every regulatory change is a deploy.
  • Rounding. Converting USD → INR involves rounding to paise. The fractional difference has to land in a rounding account, and it must be visible in reporting, not silently absorbed.

The architect-level summary: 'This isn't a distributed transaction — it's a long- running business process with compensations. I'd rather have an explicit, observable state machine with manual intervention points than an elegant design that assumes external systems behave. In cross-border payments, they don't.'"

Case 6 — Real-time fraud detection pipeline

Prompt: "Design a fraud detection system that scores every transaction in under 100ms and can incorporate new rules without a deploy."

Model answer

"The hard constraint is the 100ms budget, and the harder constraint is that fraud detection is adversarial — the patterns change, so the system must change faster than a release cycle. Those two requirements shape everything.

Budget allocation

Within 100ms, I'd plan roughly: 15ms for feature retrieval, 30ms for model scoring, 15ms for rule evaluation, and the rest as headroom for network and GC. That's tight, which means:

  • No synchronous calls to slow systems. Everything needed for scoring must be pre-computed and in a low-latency store.
  • Feature store must be Redis or an in-process cache, not a database query.
  • No JVM GC pauses in the hot path — this is a genuinely good use case for a native-image service or a tuned low-pause collector.

Two-tier architecture

Tier 1 — synchronous, in the payment path (<100ms). Returns a decision: ALLOW, REVIEW, or BLOCK. It uses:

  • Pre-computed features from a feature store: velocity counters (transactions in the last 1m/1h/24h), device and IP reputation, merchant risk score, historical chargeback rate for this card BIN, account age.
  • A gradient-boosted model (XGBoost/LightGBM) exported to a fast inference runtime. Typically 5–20ms. Complex deep models rarely fit the latency budget and rarely beat GBM enough to justify it.
  • A rules engine (Drools, or a custom expression evaluator) with hot-reloadable rules stored in a config service. This is how fraud analysts ship changes without engineering.
  • Fallback behaviour: if the fraud service times out, what happens? This is a business decision. Default to ALLOW with post-hoc review if the fraud rate is low; default to REVIEW if the loss rate is high. Never let the fraud service's outage become a payments outage unless the business explicitly chooses that.

Tier 2 — asynchronous, near-real-time (seconds to minutes). Consumes the full transaction stream from Kafka and does the expensive work:

  • Graph analysis: is this card linked to a known fraud ring through a shared device, address, or phone number?
  • Behavioural models over longer windows: is this transaction inconsistent with the user's six-month pattern?
  • Cross-merchant correlation: is this card being used at 12 merchants in 3 minutes?
  • Model retraining pipelines and backtesting against labelled outcomes.

Tier 2 can retroactively flag a transaction and trigger a hold or a step-up authentication on the next one. It can't un-charge a completed transaction, but it can stop the follow-up.

Feature computation — the part people underestimate

Velocity features ("how many transactions has this card made in the last hour") need streaming aggregation. Options: Kafka Streams with a windowed state store, Flink, or Redis with expiring counters and Lua for atomicity. The critical requirement is that offline training features and online serving features are computed by the same logic — training/serving skew is the most common reason fraud models silently degrade in production.

Feedback loop

The system is only as good as its labels. Labels come from chargebacks (slow — 30–90 days), manual review decisions (fast), and customer reports. I'd design for:

  • Immediate labels from analyst review, feeding a fast retraining loop.
  • Delayed labels from chargebacks, feeding weekly model refresh.
  • Explicit tracking of the review queue's own bias — you only get labels for what you chose to review, which means the model never learns about what it allowed. This is a genuine and often-ignored problem; the mitigation is a small random sample of allowed transactions sent to review.

What I'd monitor

  • False positive rate — the business cost, because every FP is a declined legitimate customer.
  • Fraud capture rate and dollar loss — the benefit.
  • Decision latency p99 — the hard constraint.
  • Feature drift — are feature distributions shifting away from training?
  • Rule hit rates — a rule that fires on 30% of traffic is probably wrong, and a rule that never fires is dead weight.

The trade-off I'd state explicitly: every increase in fraud capture costs legitimate customers. There's no setting where you catch all fraud and decline nobody. The job is to make that trade-off visible and tunable by the business, with the numbers in front of them — not to make it silently inside a model."

6Technical debt / modernization You can make a case for paying down debt amid feature pressure.
7Mentoring / raising the bar You multiply other engineers, not just your own output.
8Production crisis Composure, prioritisation, and blameless post-mortem thinking.
9Saying no / killing a project Judgment about what not to build. Very senior signal.
10Ambiguity / undefined problem You create structure where none exists.

Quantification cheat sheet — find your numbers

Scale

  • TPS / QPS peak and average
  • Data volume and growth rate
  • Number of users, transactions, services, teams
  • Geographic spread, number of regions

Impact

  • Latency reduced from X to Y (p99 matters more than average)
  • Cost reduced by $X/year or X%
  • Revenue enabled or protected
  • Incidents reduced / MTTR improved
  • Deploy frequency, lead time, change failure rate
  • Team velocity or onboarding time
The numbers problem
If you genuinely can't recall exact figures, use defensible ranges and say so: "I don't have the exact figure in front of me, but it was on the order of 2,000 TPS at peak." Interviewers respect calibrated uncertainty. They do not respect confident fabrication, and they will probe.

21Architect-Specific Behavioral Questions

These are written with model structures and illustrative phrasing. The [bracketed] parts are yours to replace with real specifics. Never invent a project you didn't work on — the structure is what you're learning here, not the content.

Tell me about a time you aligned IT strategy with business objectives.

Why they ask: this is the architect question. It separates people who take orders from people who shape direction. The failure mode is answering with technology.

Structure: business goal → current technical obstacle (with a cost) → your proposal → how you got buy-in → quantified outcome.

"The business wanted to [increase market share in X / reduce onboarding cost / enter a new market]. I mapped the constraint back to the technology: [specific bottleneck], which was costing us [quantified impact — X days of delay, $Y in manual processing, Z% of applications abandoned].

I proposed [approach], and I want to be clear that the technology was the easy part — the hard part was getting [finance/ops/compliance] comfortable, because it changed [their process / their risk exposure]. I ran a [pilot / proof of concept] with [specific scope] and brought back numbers rather than architecture diagrams.

The result was [metric moved from A to B], which translated to roughly [$X annually / Y% improvement]. What I'd do differently is [bring the ops team in earlier — we lost three weeks to a process objection I could have surfaced in week one]."

The tell: if your answer contains no number and no business stakeholder, it's not an architect answer yet.

Tell me about a critical architectural decision you made.

Structure: constraints → options considered (at least three) → decision criteria → choice → explicit trade-off accepted → outcome → what you'd revisit.

"We were [context]. The constraints were [latency, regulatory, team size, existing investment]. I considered three options: [A], [B], and [C].

[A] would have given us the best [scalability], but required [cost/org change] we couldn't absorb. [B] was the safe choice and the team already knew it, but it wouldn't have survived [the 2-year growth projection]. I chose [C] — [approach].

The trade-off I explicitly accepted was [higher operational complexity / a harder hiring bar / short-term delivery slowdown]. I documented that in an ADR so that when it started hurting, we'd all remember it was a deliberate choice and not an accident.

Two years on, [what actually happened]. What I'd revisit is [specific aspect] — I think I underweighted [X]."

What earns points: naming a trade-off you knowingly accepted, and showing you understand the cost is real.

Explain your last big architecture decision the way you'd explain it to our CFO.

Why they ask: architects who can't speak to finance get filtered out of senior roles regardless of technical brilliance. This tests translation ability.

"Right now, [system] costs us [$X per year] and slows us down in [a way that costs money] — every [release / transaction / new market entry] takes [time] longer than it should, and that delay is worth about [$Y].

I'm proposing we spend [$Z over N months] to change that. The return comes from three places: [cost reduction], [speed], and [risk reduction] — and I want to be honest that the risk reduction is the hardest to quantify but probably the largest, because [regulatory exposure / outage cost].

The alternative is to do nothing, which is also a choice: it means we keep paying [$X/year] and we accept that [specific consequence] will eventually become a board-level problem.

I'd like to fund this in two phases so you can stop after phase one if the numbers don't materialise. Phase one is [$] and proves [the key assumption]."

Key moves: no acronyms, a phased investment with an exit, and the explicit statement that "do nothing" has a cost. That last one is what CFOs actually respond to.

Tell me about a time you talked a team out of the technically better option.

Why they ask: this is a trap for engineers who equate "best technology" with "right decision." They're testing whether you optimise for the organisation, not the artifact.

"A team wanted to adopt [shiny technology] for [project]. Technically, they were right — it was faster, cleaner, and the benchmarks were compelling. I didn't argue with the benchmarks.

What I asked was three questions: Who operates this at 3am? How many people on the team can debug it under pressure? What's the second-order cost of a second [messaging/persistence] paradigm in an org that already has one?

The honest answer was that we had [N] people who understood it and [M] who'd need to, and we were already carrying [existing debt]. So I proposed a middle path: [use it in a bounded, non-critical service] to build real competence, with a review in six months. That gave the team their exploration without betting the platform on it.

In the end [what happened]. The lesson I took is that 'better technology' is only better if the organisation can absorb it — and the most common architectural failure I've seen isn't choosing the wrong tool, it's choosing a good tool the org can't operate."
How do you handle ambiguity in requirements?

Structure: show you make ambiguity visible and bounded rather than waiting for clarity that will never come.

Model answer: "Ambiguity is usually not a lack of information — it's a lack of decision. Someone hasn't chosen. So my job is to make the decision explicit and cheap to reverse.

Concretely: I write down my assumptions in a one-page document and circulate it. That converts 'I'm not sure what they want' into 'here's what I'm assuming; disagree in the next 48 hours.' Most ambiguity dies at that step because people will correct a written assumption but won't volunteer one.

Then I identify which ambiguities are expensive to reverse — data model, external contracts, security boundaries — and I resolve those first, because getting those wrong costs months. Anything cheap to reverse, I make a call and move, using feature flags or a pluggable interface so it's genuinely reversible.

One example: [on a regulatory project], the compliance rules were changing while we were building. Rather than guess, I pushed the rule evaluation behind a configurable rules engine and made the rule set data, not code. We shipped the platform before the rules were final, and the rules changed four times in the first month — each change was a config update, not a release."

How do you handle pushback from skeptical stakeholders?

Model answer: "First, I assume the skepticism is legitimate until proven otherwise. Usually it comes from one of three places: they've been burned before, they have a constraint I don't know about, or they're protecting something real. I try to find out which.

Then I change the medium. Technical diagrams don't persuade a business stakeholder; outcomes do. So I re-present in their language: what it costs, what it risks, what it enables.

The move that works best is giving them a bounded, low-risk way to say yes. Not 'approve this programme' but 'let us prove it on this one service over six weeks.' Skeptics usually become allies when they've been part of a small win.

And on the occasions where I couldn't convince them and they were the decision-maker — [I documented my concerns, committed fully to the chosen path, and made sure we had a checkpoint to revisit]. Disagreeing and then sandbagging is the worst possible outcome; I'd rather state my case once, clearly, and then help make their decision work."

Tell me about a time you had to say no to a project or feature.

Why they ask: saying no is a senior skill. People who can't say no preside over bloated systems and exhausted teams.

"[Stakeholder] wanted [feature/project]. I said no, and here's how I framed it: it wasn't 'no, we can't.' It was 'yes, and here's what it costs — it displaces [X], and I don't think you want that trade.'

I brought the actual numbers: [N engineer-months], which meant [specific other commitment] slips, and the ongoing operational cost of [Y]. Once the trade was visible, the conversation changed from 'why won't you do this' to 'which of these two do we actually want.'

We ended up [not doing it / doing a much smaller version]. Six months later [evidence that it was the right call — the need went away, or a vendor solved it, or the smaller version was sufficient].

What I try to avoid is the soft no — agreeing in principle and then never prioritising it. That destroys trust more than a clear no does."
How do you make build-vs-buy decisions?

Model answer: "I start with a question: is this our differentiator? If it isn't, I lean hard toward buying, because building non-differentiating software is how engineering capacity disappears.

Then I evaluate on five axes: total cost (licence plus integration plus operational, over three years — not the sticker price), time to value, lock-in and exit cost, regulatory and data-residency fit, and whether we have the skills to run it.

Lock-in gets special attention. I'll accept lock-in for a commodity where the switching cost is bounded, but not for something that touches our core data model — because then the vendor owns our roadmap.

A concrete example: [we bought our observability stack rather than building on open-source components, because the integration and on-call burden wasn't our differentiator. But we built our own reconciliation engine, because reconciliation logic is where our specific business rules live and no vendor understood our counterparties].

I also insist on a documented exit path for anything we buy. 'We could migrate in six months if we had to' is a conversation I want to have before signing, not after."

How do you balance technical debt against feature delivery?

Model answer: "I refuse to treat it as a balance, because that framing makes debt reduction a permanent loser — it never has a deadline or a customer.

Instead I make debt visible in business terms: what is this costing us, right now? 'We spend 30% of every sprint working around [system]' is a business statement. 'Our deploy lead time is three weeks, so we can't respond to a competitor move in under a month' is a business statement. Suddenly it competes for budget on equal terms.

Then I attach repayment to work that's already funded — the boy-scout rule at the architecture level. If we're touching [domain] for a feature anyway, that's when we fix the [specific debt] in the same change. That means debt reduction doesn't need its own business case.

And I hold a line on a small number of things that are genuinely non-negotiable — security vulnerabilities, anything that risks data loss, anything that blocks a regulatory commitment. Those aren't trade-offs; they're constraints.

One thing I've learned: not all debt is bad. Some of it is a deliberate loan that bought us speed we needed. The problem is unmanaged debt, not debt."

Describe a time you mentored someone or raised the technical bar of a team.

Model answer: "At architect level, my output is supposed to be the team's output, not my own commits. So I think about leverage.

Concretely, the highest-leverage things I've done: [introduced architecture decision records] so reasoning survived beyond the meeting; [ran a weekly design review] where the explicit rule was that anyone could challenge anyone, including me; [paired with engineers on their first production incident] because that's where judgment actually forms; and [wrote the internal 'how we do X here' guides] that cut onboarding from [N weeks] to [M].

A specific example: [engineer] was strong technically but froze in design reviews. Rather than tell them to speak up, I asked them to present my design to the wider team — so the stakes were on me, not on them, and they could build the muscle in a safe context. They now lead design reviews for [domain].

The measure I care about isn't how many people I mentored — it's how many decisions get made well when I'm not in the room."

Where do you see the biggest risk in our current architecture?

Why they ask: this is a judgment and preparation test. They want to see if you did homework and whether you can critique diplomatically.

Approach: do 30 minutes of research before the interview — engineering blog, tech talks, job postings (which reveal the stack and the pain). Then frame any critique as a question, not a verdict.

"I've read your engineering blog and I don't have visibility into the internals, so treat this as a question rather than an observation. Two things stood out.

First, [observation — e.g. you've grown from N to M services in two years]. At that rate, the usual pressure point isn't the services themselves, it's [the contract between them / the shared data model / the observability story]. I'd be curious how you're handling [specific concern].

Second, [regulation / market shift] seems to be changing what you need from [specific area]. That's often where existing architecture becomes expensive not because it's wrong but because the constraints moved.

I'd want to understand both before forming a view — and honestly, the answers would tell me a lot about whether this is the right role for me."

Never walk into this question with a confident diagnosis of a system you've never seen. Humility plus specific curiosity is the winning combination.

Why are you leaving after 20+ years, and why us?

Why they ask: they're checking for flight risk, bitterness, and whether you've thought about fit rather than just escaping.

Never: criticise your current employer, mention money as the primary driver, or say "I'm looking for a new challenge" (empty).

"I've had a good run at [company] — I've [specific achievement]. What's changed is that the work I want to do next is [architecture at a different scale / greenfield platform work / a domain I haven't operated in], and that opportunity doesn't exist there in the near term. That's a structural thing, not a complaint.

I've been deliberate about where I go next. I want [specific: a payments platform at real scale / a modernization programme with executive backing / a team where architecture is a function, not a title]. Your [specific thing — engineering blog, product, scale, recent funding] is why you're on a short list rather than one of twenty applications.

And I'll be direct: I'm looking for a role where 20 years of pattern recognition is an asset rather than overhead. I'd rather be the person who prevents the expensive mistake than the person who's fast at writing code."

22Pushback, Failure & Pressure Handling

Architect interviews contain deliberate pressure tests. Interviewers want to see whether you get defensive, cave instantly, or hold a position with evidence while staying collaborative.

The five pressure tactics and how to respond

Tactic 1 — "I don't think that would work." (no reason given)

What they're testing: do you fold under vague authority, or do you seek the substance behind the objection?

Response: "That's possible — can you tell me which part concerns you? If it's [component A] I'd agree, that's the weakest part of my design and here's how I'd shore it up. If it's [component B], I'd push back, because [reason]."

Never: immediately abandon your design to please them. That reads as no convictions. Also never: dig in defensively. The correct posture is curious and specific.

Tactic 2 — "That's expensive. Would you really do that?"

What they're testing: cost awareness, which is a genuine architect competency.

Response: "It is. Two things: first, I'd want to check the cost against the alternative — the current [process/outage] costs us roughly [X], so the comparison matters more than the absolute number. Second, if the budget genuinely isn't there, the phased version of this is [specific cheaper path], which gets us [partial benefit] for [lower cost], and I'd accept that as a starting point."

Having a cheaper fallback ready is what makes this answer land.

Tactic 3 — "What if I told you [constraint] makes that impossible?"

What they're testing: adaptability. Can you re-derive a design under new constraints, live?

Response: Don't defend the old design. Explicitly re-plan: "Then the [X] part of my design is out. Let me rework it — with that constraint, I'd [new approach], which costs me [trade-off] but still satisfies [the core requirement]. The parts of the design that survive are [Y and Z]."

Visibly revising your own work in real time, without ego, is one of the strongest signals you can send.

Tactic 4 — "Tell me about a failure." (then silence)

What they're testing: whether you deflect ("the project failed because requirements changed") or own it.

Structure: the decision → why it seemed right at the time → what you missed → the consequence → what you did about it → the systemic change you made afterwards.

"I approved [decision]. At the time it looked right because [genuine reasoning — this is important, don't retroactively make yourself stupid]. What I missed was [specific blind spot].

The consequence was [real impact — be honest about the size]. I was the one who had to tell [stakeholder].

What I did: [immediate remediation]. What I changed afterwards: [systemic fix — a review step, a checklist, a design principle]. The thing I took from it is [principle]. It's the reason I now [specific current behaviour]."

The killer detail: connecting it to a current behaviour. "It's why I now insist on load-testing before every peak event" proves the lesson stuck.

Tactic 5 — "A colleague disagrees with your approach. What do you do?"

Response framework:

  1. Understand their model. "What would have to be true for their approach to be better?" Sometimes the answer is "nothing, they're wrong" — but usually it reveals a constraint you didn't know about.
  2. Find the crux. Most disagreements are actually about different assumptions, not different conclusions. Name the assumption: "I think we disagree about whether [X] is likely. If you're right about that, your approach wins."
  3. Make it testable. "Can we settle this with a spike? Two days to see whether [metric] behaves the way each of us expects."
  4. Escalate on principle, not personality. If it can't be resolved, take the decision to whoever owns it with both options and their trade-offs — not a lobbying campaign.
  5. Commit and support. Once decided, you execute the decision fully, even if it wasn't yours. Say this explicitly: "I've disagreed and lost before and I commit completely — half-hearted execution of a decision you opposed is the worst of both worlds."

Behaviour under live design pressure

Do

  • Think out loud — they're scoring your reasoning, not your conclusion
  • Say "I'm not sure, let me reason about it" — it's a strong signal, not a weakness
  • Write down their constraint before responding to it
  • Summarise the trade-off before making a choice
  • Ask "does that answer your question, or should I go deeper?"
  • Admit when you're at the edge of your knowledge — and say how you'd find out

Don't

  • Go silent for 60 seconds — they can't score silence
  • Bluff. Senior interviewers detect it instantly and it's fatal to trust
  • Argue with the premise instead of engaging with it
  • Over-engineer. Proposing Kafka + Cassandra for a 100-user internal tool is a red flag
  • Mention technology you can't defend when challenged
  • Apologise repeatedly. One acknowledgement, then move on

Reference implementation — thread-safe rate limiter

/**
* Token-bucket rate limiter.
* Design notes:
* - Refill is computed lazily on acquire() rather than by a background thread.
* This avoids a scheduler, survives GC pauses, and is cheaper at low QPS.
* - The lock is only held for arithmetic — no I/O, no allocation, no callbacks.
* - Time uses System.nanoTime() because it is monotonic; currentTimeMillis()
* can jump backwards on NTP correction and would break the bucket.
*/
public final class TokenBucket {

private final double capacity; // max burst
private final double refillPerNano; // steady-state rate
private final Object lock = new Object();

private double tokens;
private long lastRefillNanos;

public TokenBucket(double capacity, double refillPerSecond) {
if (capacity <= 0 || refillPerSecond <= 0)
throw new IllegalArgumentException("capacity and rate must be positive");
this.capacity = capacity;
this.refillPerNano = refillPerSecond / 1_000_000_000d;
this.tokens = capacity;
this.lastRefillNanos = System.nanoTime();
}

/** @return nanos until the next token is available, or 0 if acquired. */
public long tryAcquire() {
return tryAcquire(1);
}

public long tryAcquire(int permits) {
if (permits <= 0) throw new IllegalArgumentException("permits must be positive");
synchronized (lock) {
refill();
if (tokens >= permits) {
tokens -= permits;
return 0L;
}
double deficit = permits - tokens;
return (long) Math.ceil(deficit / refillPerNano);
}
}

private void refill() {
long now = System.nanoTime();
long elapsed = now - lastRefillNanos;
if (elapsed <= 0) return;
tokens = Math.min(capacity, tokens + elapsed * refillPerNano);
lastRefillNanos = now;
}
}
What makes this a strong interview answer
The comments explain why, not what. You chose lazy refill over a background thread and said why. You used nanoTime for a reason you can defend. You return the wait time instead of blocking, which pushes the policy decision to the caller. And you validated inputs.

In the interview, also say: "This is per-instance. If the limit has to be global across pods, the bucket state moves to Redis and I'd use a Lua script to make the refill-and-decrement atomic — at the cost of a network round-trip per acquisition, which I'd amortise by acquiring in batches."

Low-level design: the 6-step approach

  1. Clarify scope — which operations are in, which are out. Write them down.
  2. Identify entities and their relationships — nouns become classes; be ruthless about which nouns actually deserve to exist.
  3. Define interfaces before implementations — this is what "design" means in LLD.
  4. Choose data structures and justify them — "HashMap for O(1) lookup, TreeMap for ordered expiry" is the level of specificity expected.
  5. Handle concurrency explicitly — where are the locks, what's the granularity, what's the contention point?
  6. Extensibility — "if we needed to add [X], here's where it plugs in."
The most common failure at senior level
Over-abstraction. Twenty-year veterans sometimes produce AbstractPaymentProcessorFactoryStrategyImpl for a problem that needed three classes. Interviewers read this as "will slow the team down." Start concrete. Add abstraction only when you can name the second concrete case it serves.

Code review round — what to look for

  • Concurrency: shared mutable state, non-atomic check-then-act, missing volatile, lock ordering that could deadlock, locks held across I/O
  • Resources: unclosed streams/connections, missing try-with-resources, ThreadLocal not cleared in a pooled thread
  • Persistence: N+1 queries, missing index on a filter column, unbounded query without pagination, transaction spanning an external call
  • Correctness: floating-point money, off-by-one, null handling, timezone-naive dates, string comparison with ==
  • Security: SQL built by concatenation, secrets in code, PII in logs, missing authorisation check
  • Design: a class doing three things, a method with seven parameters, a public setter that breaks an invariant

Adjust for reality

The five rules of negotiation

1. Never give the first number

If asked for expectations early: "I'd rather understand the scope and level first — what range is budgeted for this role?" If pressed: "Based on my research for a role at this level in this market, I'd expect something in the [range], but I'm flexible on structure if the scope is right." Give a range where your target is the bottom.

2. Negotiate the whole package

Base, bonus (target % and actual payout history), equity (type, vesting, current valuation, refresh policy), sign-on, relocation, vacation, remote flexibility, learning budget, title. Sometimes the base is fixed but the sign-on and equity aren't.

3. Competing offers are your only real leverage

Not bluffs — real ones. Interview at multiple places on overlapping timelines. "I have another offer at [X]" changes the conversation entirely. A bluff that gets called is a lost offer.

4. Negotiate once, properly

Don't nickel-and-dime across five rounds. Make one well-reasoned counter with your full ask, and be ready to accept. Repeated small asks read as bad faith.

The counter-offer script

"Thank you — I'm genuinely excited about this, and I want to accept.

I do want to talk about the number. Based on [my research / the range you shared / another offer I'm holding], I was expecting something closer to [$X]. Given [specific: the scope of the modernization programme / my 20 years in regulated payments / the fact that I'd be stepping into an architect role with team-wide responsibility], I think that's a fair reflection of the value.

If [$X] isn't possible on base, I'm open to getting there through [sign-on / equity / an early review at six months]. What's possible?"

Why this works: enthusiasm first (you're not a flight risk), a specific number with a reason, an alternative path so they can say yes without breaking the band, and an open question rather than an ultimatum.

Handling the hard moments

"That's above our band for this level."

"I understand. Can we talk about the level then? If the scope of this role includes [architect-level responsibility], I'd expect it to map to a different band — and if it doesn't include that, I'd want to make sure we're aligned on what the role actually is."

This is often the real negotiation: not the number, but the level. Getting re-levelled is worth more than any sign-on.

"What's your current compensation?"

In many US states, employers can't ask this. Where they can:

"I'd rather focus on the value of this role than my current package, since they're different scopes. What range have you budgeted?"

If they insist and you want to answer, give total comp including equity and be clear it's total, not base — then immediately pivot to your target.

"We need an answer by tomorrow."

Usually artificial urgency. "I'm very interested and I want to give you a considered yes rather than a rushed one. I have another conversation finishing [day]. Can we speak [day + 2]?"

If the deadline is genuine, they'll say why. If it's pressure, they'll accommodate. A company that won't give you 48 hours is telling you something about how it operates.

You have no competing offer

You still have leverage: your experience, the difficulty of the search, and their sunk cost in the interview loop. Use market data instead: "Based on levels.fyi data for this level at companies in this tier, the range is [X–Y], and I'm targeting [Z]."

And never say "I have no other offers" — say "I'm in conversations elsewhere" only if true, otherwise simply don't raise it.

Questions to ask them (that signal seniority)

  • "How are architecture decisions made here, and who has the final call when there's disagreement?"
  • "What's the biggest technical risk on the roadmap in the next 18 months?"
  • "How does this role interact with the business — do I present to [finance/product/board]?"
  • "What happened to the last person in this role, and why?"
  • "How is technical debt funded? Is there a standing budget or does it compete with features?"
  • "What does success look like at 6 and 12 months, concretely?"
  • "What's the on-call expectation for architects?"
  • "How many people here have been promoted internally into architect roles in the last two years?"

The last one tells you whether the role is a real function or a title they hand to people to keep them quiet.
